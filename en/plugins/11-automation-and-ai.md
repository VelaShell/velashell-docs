# 11 · Automation and AI

Both are "application layers above the plugin system" and share the same
principle: **the host provides the skeleton and security boundaries, while
plugins provide the substance**.

## 1. Automation (S5/S6)

### 1.1 Model: Rule = Trigger + Condition + Action

```text
Trigger           session connected / transfer completed / scheduled (cron) / manual command / plugin-defined trigger
Condition         when expression (reuse 03 §6 grammar): host matching, time window, previous result…
Action            built-in actions (execute remote command, upload/download, send notification, write to terminal…)/ plugin-defined action
```

The **host** owns the rule itself (storage, scheduling, execution orchestration,
and logs). Plugins participate in two deliberately separate ways:

1. **A plugin consumes host events and does its own work** (07 §8's
   `vela.events` + capabilities): suitable for complex logic, with every action
   covered by that plugin's permissions and audit trail.
2. **A plugin contributes triggers/actions to the rule engine** (manifest
   `contributes.automation`): users visually compose them on the host's
   "Automation" page and use plugin capabilities as building blocks. During
   execution, the host calls the plugin back (`automation/evaluateTrigger`,
   `automation/runAction`); action execution remains subject to the plugin's
   own permissions, so the rule engine does not amplify permissions.

### 1.2 Security Boundaries

- Rules can be created or modified only by the **user in the host UI**. A plugin
  can only "suggest" a rule (`SuggestRuleAsync`, which displays a confirmation
  card), never create one silently. The combination of automation and
  `remote.exec` is powerful enough that a human must remain in the loop.
- Each rule displays an aggregate of the permissions it will use. Rules
  containing highly sensitive actions (`remote.exec`/`terminal.write`) require
  item-by-item confirmation before their first run, with an option to
  "automatically run this rule in the future."
- Rule execution history (time, trigger reason, action-output summary, and
  success or failure) is persisted; failures can be rerun with one click. After
  N consecutive failures, the rule is automatically suspended and a notification
  is sent.
- Plugins awakened by cron triggers use the `onSchedule` activation event and
  are subject to load staggering and a minimum interval of 1 minute, preventing
  a plugin from turning the host into a request blaster.

### 1.3 Built-In Actions (Provided by the Host, No Plugin Required)

Execute remote commands (exec channel), upload/download files, send
notifications, open sessions, write to the terminal (highly sensitive), and run
local programs (highly sensitive, explicit path). This makes lightweight
automation available without plugins, while plugins handle the long tail.

### 1.4 Managed execution and recovery in the AI plugin (SDK 2.1.0)

This records added AI-plugin source behavior, separately from the rule engine above and the future host AI gateway below. It does not declare a gateway or universal permission system implemented.

**Managed commands** live only while the application runs, without disconnect/restart recovery:

| Tool | Parameters and behavior |
| --- | --- |
| `run_command` | `timeoutSeconds=0` means no execution deadline by default (explicit values capped at 86400); `waitSeconds=2`, maximum 10, is only a short wait window: expiry returns running/taskId, not termination; `monitoring=false`; `elevated=false` |
| `run_on_sessions` | Up to 16 targets queue for four shared stream slots; cancelled unstarted items do not start or collide directly with the host concurrency limit |
| `task_status` | `taskId`, `cursor=0`: state and incremental output |
| `task_wait` | `taskId`, `waitSeconds=2`, maximum 30, `cursor=0`; waiting expiry is neither an execution deadline nor cancellation |
| `task_cancel` | Requests cancellation of this run's task; cleanup is not blocked by revoked read scope |

States are Starting / AwaitingUser / Running / Succeeded / Failed / Cancelled / TimedOut / Unknown. Ordinary results preserve stdout, stderr, exit code and timeout/truncation information. Sudo output is `combined`, preserving raw newline/CR fragments without pretending to provide stderr. Cancellation after starting, without confirmed remote termination, is Unknown with `cancellationRequested=true` and `remoteStopConfirmed=false`. Two exceptions are recorded as Cancelled (also `remoteStopConfirmed=false`, but the run does not pause): an elevated command cancelled while still in approval/authentication, before the user command reported starting, and an explicit monitoring task stopped by name with `task_cancel`, which is the normal way to end one (cancelled along with a whole-run Stop, it is still Unknown). Cancellation before opening the stream is Cancelled with confirmation it never started. SSH disconnect or sudo Exited without an exit code is Unknown. TimedOut after starting without stop confirmation also blocks further automatic tool side effects in that run; the framework never replays it. Authentication cancellation/failure/unsupported explicitly means the user command did not start, without ordinary fallback.

Each run retains at most 128 tasks at once. At the cap, tasks that have finished and whose terminal state was already delivered are reclaimed; Unknown and unconfirmed-stop TimedOut tasks are not, because they are the run's stop boundary. Output uses a thread-safe bounded queue (32K characters, 256 entries, at most 4096 characters per entry; an oversize fragment is split into consecutive entries, not truncated); `NextCursor` / `EarliestCursor` / `OutputTruncated` identify earlier output evicted by those limits. taskId is readable only in its creating run scope, bound to entry point/conversation/fixed sessionId, not shared across chats or MCP clients. Session scope is rechecked at start, query and completion; see [Security §1.1](12-security-threat-model.md#11-actual-boundaries-of-this-sudo-and-managed-ai-execution-change-sdk-210) for cache/revocation limitations.

Commands must remain foreground processes in the managed channel. Arbitrary shell `&`, nohup or daemonize is not parsed/rewritten; independently detached processes are not monitored, and parent exit does not prove completion. Explicit `monitoring=true` infinite logs wait locally for exit or Stop without auto-waking/polling the model.

**Elevation has two explicit approval layers.** `elevated=true` takes the actual command without sudo; root scope includes all pipelines and redirections. Plugin Ask/ReadOnlyAuto uses distinct approval with no first-word approval memory. Bypass skips only the plugin card, never trusted host confirmation on each call, including NOPASSWD. The external MCP route has no approval card: elevation is not rejected at the plugin layer, and in every mode it goes straight to the host's desktop confirmation and password prompt (which cannot be forged or skipped); other writes are still rejected under Ask/ReadOnlyAuto. The initialize instructions tell the external agent to use `elevated=true` and that the task reads `AwaitingUser` while the prompt is open. A plain `sudo` inside an ordinary command has no terminal on the separate channel and fails as soon as sudo wants a password; the receipt's `hint` field then points back to `elevated` (nothing is rewritten automatically: running the whole command as root would change the meaning of commands such as `make && sudo make install`). Passwords never pass through the plugin or model. This is not terminal autofill; see [Capability APIs §3](07-capability-apis.md#3-velaremoteexec-remote-execution-s5s6).

**Rejection is a run-level stop boundary.** Plugin approval returning false/missing a Handler, or host AuthenticationCancelled (including root confirmation refusal/password cancellation), marks the current run denied. Before model requests, tool calls and background terminal continuation, guards force an `ExecutionDenied` pause with localized desktop/Bridge feedback, rather than relying on the model obeying a “do not retry” string. A new desktop/Bridge user turn creates a new run; the denied run cannot continue side effects. External MCP is the exception: each client McpToolHost still has one fixed scope (so background tasks remain queryable), but a denial is only that call's result and does not seal the connection. Later tools keep working (after read-only auto-approval refuses a write command, `list_sessions` still works), and whether to stop is up to the MCP client.

**Approval modes** (tightened on 2026-10-25): "read-only auto" lets through only `run_command`s whose shape is known not to change anything — `sudo …` always asks, `env` is off the list (`printenv` stays), and words are split on spaces and tabs;
`curl` is allowed only with the few options that GET / HEAD an explicit `http://` / `https://` URL to standard output, while writing files, uploading, sending data, changing the method, custom headers, reading config files and non-http(s) protocols all ask;
`wget` writes to disk by default and is allowed only with `-O -` / `-qO-` and `--spider`; a dozen more commands on the list that change state when given certain arguments are judged by those arguments (`ip` only show / list / get; `route add`, `ifconfig eth0 down`, `mount -a`,
`hostname x`, `date -s`, `dmesg -c`, `journalctl --vacuum*`, `ss -K`, `rg --pre`, `bat --pager`, `less +!cmd` and the like ask), and when their arguments contain quotes, backslashes, `$`, wildcards or braces the guess about what the shell would expand is abandoned and it asks.
Tools of external MCP servers always go through approval (`readOnlyHint` only affects retries), and the approval callback and mode are **per round** (`McpApproval`, passed in by the caller each round): concurrent IM chats each ask for themselves, nothing crosses over to another chat,
and another chat being on "auto approve all" no longer skips the question. The plugin's own external MCP service offers **no tools at all** in "Chat" mode (`tools/list` is empty and the initialize instructions suggest switching to Plan or Agent).

Desktop MCP management uses the current chat panel's `McpManager` to show Stopped / Starting / Ready / Degraded / Failed / Stopping, tool counts and sanitized errors, with start, stop, restart and live catalog refresh actions. Actions use saved configuration; temporary connection tests do not change runtime state. `AutoStart=false` requires explicit startup, manual stop suppresses automatic reconnection, and old tools and pending approvals are cancelled with the connection. Removing, disabling or changing connection parameters closes the old connection; workspace authorization is checked again before reuse. Closing the window stops status polling and cancels pending startup. The IM bridge has a separate manager and is not controlled by desktop buttons.

Desktop and IM turns hold connections through `AcquireToolsAsync` leases. With `KeepAlive=false`, the connection closes only after the last user releases it, preserving other concurrent turns. Stdio `EnvironmentInheritMode` supports Minimal (default SDK essential system variables), None (explicit variables only), and All (all host variables); explicit settings override inherited values. Existing configurations also default to Minimal. Proxy and custom runtime variables must be provided explicitly; All may expose host environment secrets to the server.

Windows Stdio supports executable paths containing spaces. Configure the command and arguments separately, double-quoting argument paths containing spaces. To address the SDK's `cmd /c` first-command quoting issue, these program paths use a `/d /c @` wrapper without the second argument expansion introduced by `call`. A real .NET test process has verified environment inheritance/overrides, working directory, handshake and calls, stop/restart/disable, last-lease release and process exit after startup timeout on Windows. This does not constitute acceptance on Linux/macOS or for arbitrary third-party servers.

Desktop Agent's `delegate_subagent(prompt, role?, modelId?, allowWrites=false, timeoutSeconds?)` can select a configured chat model under any provider instance the user has added (since 2026-11-18; the parent model's provider is listed first). Its tool description lists model configuration IDs, names, providers and real model ids; omitting the ID inherits the parent model at delegation time. The main model may delegate substantial independent work automatically without a separate decision model; it handles small tasks directly. It chooses by the listed facts first and may use what it knows about a well-known vendor model's strengths when the model id clearly identifies it; unrecognised names count as unknown, and the facts win when they disagree. Each turn allows at most 8 tasks, 4 concurrently, with a default 120-second limit (`timeoutSeconds` accepts 30–600 seconds; time spent waiting for approval or queued behind the file-mutation lock is not counted). Tasks inherit the parent's local/SSH read-only tools and filtered MCP tools by default. Explicit `allowWrites=true` enables existing local/remote file mutations under the parent's scope, disabled-tool list, current approval policy and denial boundary. Commands, session/approval management, transfers and recursive delegation remain excluded; MCP remains read-only. Parent and child built-in file mutations share cancellable serialization from read through approval to write. Other chats, external programs and MCP are not coordinated, and cancellation/failure does not promise rollback. Results include `allowWrites`, `modelId`, `toolsUsed` and errors; chat cards show the model and live state. Independent models use their own credential resolution and endpoint-scope validation. Tasks never store keys. Candidates cover every provider instance (told apart by instance ID, so identically named instances stay separate); unknown/deleted models, image models and changed parent credentials fail explicitly. Tool protocol rejection never falls back to tool-free chat. A configured model that the server reports as not available for this account (see the end of §1.8), or whose provider rejects the credentials, is out of quota (401 / 403 / 429) or fails an OAuth refresh, is, while the subtask has no output and no tool calls, rerun on the parent model and then other candidates (the parent's provider first), with the switch stated on the card and in the result and the model marked unavailable for the turn; this differs from the configuration-level failures above and does not widen the candidate set. Desktop candidates are reordered after failover; IM orders them by the turn's parent provider. External MCP lists the provider of the model selected at connection creation first, or the first chat model's provider if none is selected; delegation is not exposed only when no chat model exists at all. Provider tool capabilities are not fully declared, so an empty `toolsUsed` does not prove that files were read. See the [actual permission boundaries](12-security-threat-model.md).

Subtask headers use a plugin-specific theme, small Lucide chevrons and fine separators, preserving native Expander state binding and keyboard operation. The footer usage reads `↑cumulative input ↓cumulative output | context meter ctx 21% · cache 80%`: cumulative input/output appear from the start of the first request, and the meter sits right next to its percentage. The whole area is a button (`UsageButton`). Hovering opens `UsageDetailView`: the total with a window-percentage badge; a bar segmented by source (system prompt / built-in tools / MCP tools / compaction summary / messages) with the auto-compaction line `ContextCompactor.TriggerTokens` = (window − max output) × 0.75 drawn as a tick, followed by the compaction buffer and the reply reserve; a caption saying how much is left before that line, in the warning colour when close; one row per category; the prompt-cache read-written-uncached bar for the last request; and conversation input-output-reasoning-cost. Clicking opens `ContextDetailView` in `ContextPopup`, the counterpart of Claude Code's `/context all`: findings first (MCP servers never called in the current context and the tool definitions they occupy, the tool-result share of messages and the largest one, the fixed cost of system prompt plus tool definitions, a note when compaction is off), then a 20×10 cell grid (each cell is 1/200 of the window, including free / compaction buffer / reply reserve) with a totals table, and messages, built-in tools and MCP tools expand down to single content parts, single tools and single servers. The hover panel steps aside while the popup is open; Esc closes it. Categories come from the `onRequest` observer on `SteeringChatClient`: before every real request (tool continuations included), `ContextBreakdown.Analyze` splits the messages actually sent and `ChatOptions.Tools` (tools estimated from name + description + parameter schema; MCP tools grouped by server through `McpManager.ServerOf`; the user message identical to the conversation summary and in-run `<run-progress-summary>` blocks count as summary) and stores the result on the conversation's `Breakdown`. The panels scale it proportionally to the reported input (`ContextUsage`); while streaming nothing is scaled and the extra goes to messages. Conversations restored from history show only the total until their next request. The plain-text breakdown remains both views' `ToString` and the screen-reader HelpText. In-flight text, reasoning and tool arguments use character-weight estimates marked `~`; reported usage replaces estimates when the stream ends, including failed attempts and auxiliary requests. Input images use a fixed allowance; estimates exclude tool schemas, never enter cost accounting, and are not cache-write counts. Cache writes: the Anthropic adapter reports `CacheCreationInputTokens`; the Microsoft.Extensions.AI.OpenAI 11.0 Chat Completions / Responses adapters drop `cache_creation_input_tokens`, `*_tokens_details.cache_write_tokens` and `prompt_cache_hit_tokens`, so `CacheUsageChatClient` recovers them from the SDK's raw usage via `ModelReaderWriter` (same key; reads are filled only when missing). Official OpenAI does not report writes, and the panel says so. New conversations clear the counters; background conversations do not overwrite the foreground.

For known windows, context text and the meter appear from request start with a `~` estimate of current input plus generated output, never cumulative conversation usage. The previous request's cache-hit rate is hidden during generation. Completion restores the last reported request input ratio and cache information; unknown windows still have no percentage.

Desktop `AgentPausedException` handling uses a notice card and Warning log while preserving interrupted history and the unknown-outcome stop boundary. A remote execution timeout does not prove process termination and never triggers automatic replay. The `run_command` description recommends keeping the default `timeoutSeconds=0` for long operations and using `waitSeconds` to return a task ID early.

Subagent cards start collapsed, showing the task summary, role, localized state, elapsed time, total tool calls and error count; the group shows how many tasks have finished. Expand a card for the full request, model, tool details, complete errors and Markdown result, with long content scrolling inside the card. State updates preserve expansion and do not force scrolling to the bottom. Both initial insertion and subsequent updates preserve the parent reply's streaming Markdown segment, preventing tables, emphasis and code fences from being split across renderers.

Execution and result delivery: a subtask is run by `SubagentRunner`, which is independent of the UI. It does not inherit the parent conversation, carries its own system prompt, and reuses the main loop's `RecoveringChatClient` / `AgentExecution` (transient-failure retries, truncated tool calls never executed, repeated identical calls stopped, one nudge after an empty reply that follows tool calls). It runs as a streaming request for at most 30 steps. The final report is the text after the last tool call; a missing or truncated report is recorded in `errors`. Once a subtask reaches a terminal state, `AgentRunCoordinator` delivers every result that has not been collected yet to the parent model as an `<untrusted-subagent-results>` notification, on the same path as background commands, and the parent turn does not end before that. Results already collected through `subagent_wait` / `subagent_status` are not delivered again, and those two tools do not count toward the no-progress pause while the status keeps changing. Timeout, cancellation and failure keep the text written so far and flag it with `outputIsPartial`; the report handed to the parent model is capped at 24,000 characters while cards and history keep the full text. Subtask usage is added to the conversation totals. Approval requests raised by a subtask carry `Origin`, which the approval card shows. Running cards show the current activity (the tool being called and its target, waiting for approval, or waiting for the file-mutation lock), tokens and a per-task cancel button, and are stored and replayed through `ChatTurnMeta.Subagents`; `subagent_wait` / `subagent_status` calls produce no separate tool card. The IM bridge and the external MCP endpoint reuse the same `SubagentRunner`. The IM bridge creates one orchestrator per turn (Agent mode); scope, mode and approval follow that chat's grant, inheriting the parent model uses the credential the turn is running with, and any other model is resolved from the current settings. The progress message ends with the number of finished subtasks, approval messages name the originating subtask, and subtasks still running are cancelled when the turn ends. The external MCP endpoint creates one orchestrator per connection (`McpToolHost.CreateAsync`, Agent mode with at least one configured chat model); subtasks use the chat model currently selected in VelaShell and consume the user's model quota. This path does not wake external models (`DeliversResults=false`), so the receipt and tool descriptions tell the caller to use `subagent_wait`. Each connection allows at most 32 subtasks, 4 concurrently; a running subtask keeps the connection from idle eviction, and closing the connection cancels them. `subagent_wait` / `subagent_status` / `subagent_cancel` do not take the tool-call serialization lock.

**Recover model steps, not whole side-effecting turns.** Desktop chat and Bridge share a per-conversation serial coordinator. The runId + CallId ledger reuses in-flight/completed results for the same id and arguments, pauses on the same id with different arguments, and does not deduplicate all identical commands under different ids. Tool frames are released only after a complete ToolCalls step with validated complete arguments; incomplete calls/reasoning are not replayed. Complete model steps and paired tool results form checkpoints. Partial prose is retained with an explicit localized continuation boundary, without promising unprovable seamless deduplication; when only whitespace arrived before a disconnect, the request is resent as is, with no whitespace-only assistant message and no continuation boundary. Argument-binding errors (a missing required argument, or a JSON value that cannot be read as the parameter type, caught before the tool body runs and therefore without side effects) go back to the model as tool errors to correct and retry; a single one does not pause, and getting the call right after two corrections is unaffected. Three consecutive steps that call tools but run none of them (binding failures, or same-CallId calls that only get the ledger's earlier result back) pause with `NoProgress`. Other tool failures still pause and their side effects are never retried automatically.

Normally completed model steps containing only role/usage/whitespace also enter recovery; prose, standard/raw reasoning and complete tool calls are not empty. An ending by the output limit / a content filter / a refusal with visible text (and no tool call in that step) **completes normally** (since 2026-10-25): the desktop panel shows a warning-colored notice card and Bridge appends a line to its reply, with no error, no failover and no switch back to the original relay, recorded as a healthy success; with no text at all it still fails, without retry or failover; error content is not retried as an empty reply; a Responses `response.failed` (which the adapter turns into one empty update) fails with the server's own words — before, a stream that had produced half an answer was recorded as a success and thawed the cooldown, and one with no text was retried as an empty reply and lost the server's message. An empty final step after tool calls gets one extra request with a "please continue" (sent only in that request, never added to the history); if it is still empty the turn ends normally with an explanation, recorded neither as a failure nor as a cooldown, and the empty step stays out of the history. Empty steps and transient network/429/appropriate 5xx failures share at most two recoveries per step (default 400/800ms, respecting available Retry-After; values above 120 seconds pause with a dedicated reason, without retrying early or first announcing a retry or an execution-budget limit; the pause still carries the original 429 / 503, so the desktop panel's key rotation and failover work as usual on the first step). Every actual request passes Steering account/credential revalidation; cancellation, rejection and deterministic errors are not retried. UI 25-step and Bridge 20-step boundaries only segment execution: continuation is automatic using the same tool ledger and checkpoint, without removing tools or requiring confirmation for every batch. The cumulative hard limits of 100 model steps, 200000 output tokens and eight batches no longer apply. Batch progress shows only the actual batch number, not a fictitious total; background-completion wakeups do not increment it. Context utilization is only the input of the turn's last request relative to the model window (not the sum over the steps of a multi-step turn), not execution progress or remaining execution allowance; per-request output limits and existing context compaction/trimming remain independent, and context within a turn is tidied in stages as described in §1.13. All reported input/output usage from successful and failed attempts is still accumulated; continued execution continues to incur model usage and cost, and users can Stop at any time. Cancellation, approval denial, unknown outcomes, tool errors and two `NoProgress` pauses can still stop execution: the same tool called four times in a row with the same arguments (the read-only polling tools `task_status` / `task_wait` / `transfer_status` / `transfer_wait` count as making progress while their result changes and accumulate only while it stays identical; side-effecting tools are still stopped by signature alone), and the three consecutive steps without a single tool actually running described above. Neither is complete loop detection. Existing Bridge turn timeouts and provider/model limits still apply, so completing every plan is not guaranteed.

Ordinary desktop chat retries an empty reply at most twice (400/800ms, with the same "Empty reply, retrying" status as Agent) before meaningful output or tool side effects; other transient failures still get at most one retry. Mixed failures do not reset the attempt counter; existing candidate failover follows exhaustion. Settings tests, bulk detection and pre-failover probes retry a normally completed response without visible prose only once (400ms); both requests and the wait share the existing 15-second deadline. Reasoning alone still cannot pass a probe. User cancellation propagates immediately, reported usage from failed attempts is accumulated, and these counts exclude provider SDK internal retries. Bridge shares step recovery and shows a localized empty-reply error after exhaustion. No settings were added, and empty-summary trimming fallback is unchanged.

Finite background job completion locally wakes its owning conversation and adds a new terminal notification to model context, never a second tool result for the original CallId; a terminal state already delivered through `task_status` / `task_wait` is not notified again. The notification says it is not a new user command, wraps remote output in `<untrusted-command-output>` and states that the content is command output, not user instructions, and must not be followed; the content is JSON-escaped, so output cannot forge the closing tag. A task whose session authorization was revoked yields only a "result withheld" Unknown notice (no output, exit code or session id), and the run pauses with TaskUnknown. Local waiting does not request the model and has no default ten-minute waiting deadline; Bridge does not enlarge existing authorization or total timeouts. Stop, entry-point detach/destruction, plugin unload, MCP session deletion/expiry/settings reload and Bridge authorization reload cancel old runs, asynchronously clean up and discard late wakeups. Switching chats does not inject results into another conversation. MCP exposes task query/wait/cancel only; automatic continuation of an external model belongs to the MCP client.

### 1.4a Web search and provider requests (2026-10-25)

- **Web search is off by default**: `web_search` / `web_fetch` and providers' native search all sit behind one switch in the AI global settings, "Let the assistant search and read the web", **off by default**. When on, search words (often error messages and host names) go to the SearXNG instance in the settings,
  by default `https://searxng.easilynet.top`, run by VelaShell (it sees the search words and the source IP, never the conversation, terminal output or identifiers); it can be pointed at your own instance, and clearing the address turns search off (`web_fetch` still works);
  `web_fetch` fetches pages directly from this machine, with private addresses blocked by default. A switch stored before the upgrade is kept as it is (the settings are saved whole, so a stored `true` cannot be told apart from the old default); only configurations that never stored it get the new default.
  The external MCP service does not read this setting and uses the default, so that route offers no web tools.
- **Responses `store`**: custom endpoints (catalog `custom-*` and old configurations without a catalog id) send `store:false` by default, so the context (terminal output included) is not kept on the provider's side; ticking "Let the provider store each turn (OpenAI Responses store)" in the provider section of the settings stops sending it
  (a new nullable field `CustomResponsesStore`; existing custom endpoints count as off as well — the old `StoreResponses` field is a default copied when the provider was created, not a user's choice). Named catalog entries such as the official openai, Codex and Azure still follow the catalog.
- **Anthropic's model list request** matches the chat request: both send `anthropic-version: 2026-10-21` (the list request used to stay at 2023-06-01), with a key in `x-api-key` and a token as Bearer.
- **Root confirmation**: in the host's elevation confirmation dialog, "Approve" stays disabled for about 0.6 seconds after it opens (counted from the window opening), Cancel is always available, and Enter and the initial focus stay on Cancel.

### 1.5 Model lists in the AI plugin settings

Provider model lists in the settings sidebar are collapsed by default, regardless of model count; each provider row still shows its model count. When opening settings, if the active model's provider is collapsed, its provider row is selected without automatically expanding the list; if it was saved as expanded, the active model remains selected. The chat model is unchanged. Click a provider row or press → to expand and ← to collapse; manual choices are saved. Explicitly adding or navigating to a model still reveals it for editing.

### 1.6 AI file uploads and progress (SDK 2.1.1)

> This section and §1.7 describe default approval flows. Independent external MCP upload/download auto-approval switches use the official SDK 2.1.9 and are integrated on the host development branch. Both default off and do not affect desktop AI, remote-link saves or IM. Users need a host version containing the feature. See [Collaboration §2.3c](collaboration.md#mcp-transfer-auto-approval) for configuration and exceptions.

This section concerns only `upload_local_file`: streaming a file from the user's **local machine** to an authorized SSH session through SFTP. It does not put arbitrary large files into model context, change chat attachments or bypass IM platform `send_file` limits. Removal of the two download-entry size caps is covered separately in §1.7. Uploads have no fixed AI file-size cap, but local/remote storage, authorization, protocol and connection constraints still apply.

| Tool | Behavior |
| --- | --- |
| `upload_local_file` | Absolute local and remote file paths and optional session; `overwrite=false` preserves an existing destination by default, and explicit replacement still requires approval. Returns a structured job snapshot rather than waiting for an entire large file |
| `transfer_status` | Reads this run's `transferId`: state, 64-bit transferred/total bytes, speed, ETA, generation and safe-resume availability |
| `transfer_wait` | Short wait, default 2 seconds, maximum 30; expiry never cancels the upload |
| `transfer_cancel` | Requests cancellation using job id and expected execution generation; requested does not mean remote termination confirmed |
| `transfer_resume` | Only when the host explicitly reports `CanResume`, with fresh approval and target-connection validation; never silently restarts from zero |

Snapshot `transfer_id` identifies the background job, `generation` distinguishes resumed execution, and `sequence` rejects stale progress. Interpret `stillRunning` with explicit state: all bytes may be present while verification/commit is pending, so full percentages are not success. Only `Succeeded` is successful. Failed, cancelled and `Unknown` outcomes are never automatically replayed; a lost commit acknowledgement must be resolved before another id can overwrite the destination. After a cancel, deadline, disconnect or plugin stop, the host waits up to 30 seconds for the backend to actually stop (an SFTP cancel must drain writes already sent, then wait for the `CLOSE` reply). Only then is the stop confirmed and the remote temporary cleaned up; otherwise the outcome is `Unknown`. An SSH disconnect ends as `Failed` / `session-disconnected`, not `Cancelled` (`Cancelled` means someone no longer wants the transfer, so the caller should not send it again). That state is reached only when the write is confirmed stopped and the destination is confirmed unwritten (`destinationCommitConfirmedAbsent`), so the model may safely start the transfer again after reconnecting. A disconnect while a commit request is outstanding stays `Unknown` / `commit-unknown`.

The host owns approved uploads, separating request/model-wait lifetime from transfer lifetime. Status/short waits do not require a model-generation connection or repeated model requests to refresh progress. AI tasks are owner/run isolated, with session authorization rechecked on queries and completion; revoked paths/results are withheld. Initial receipts and final completion notifications are separate, never a second tool result for the original CallId. External MCP agents explicitly query/wait for progress; the server does not wake an external model.

Uploads stream rather than load whole files into memory. After resolving parent-directory aliases, the opened source handle is verified by **file identity** (Windows volume serial + file id, Linux / macOS dev + inode), reached without following any link; mapped drives, subst drives, other hard-link names and case- or Unicode-normalization variants are accepted as the same file (since 2026-10-25; before, the handle's final path was compared character by character and all of these were wrongly refused). Approval shows the resolved path; symbolic links at the file itself are unsupported. Windows holds a source handle denying shared writes/deletion. Unix does not treat FileShare as a guarantee against other writers, so before uploading, Linux / macOS take a host-private snapshot of the source and verify it byte-for-byte (by digest) against the source handle. The snapshot lives **on the source file's own volume** (since 2026-10-25; before, it always went to the system temporary directory, where a snapshot of several GB ate memory when /tmp was a tmpfs): a hidden `.vela-snapshot-<48 hex>` file in the source directory, unlinked right after creation and kept alive by the open descriptor, so a host crash leaves no plaintext copy. Where the volume supports copy-on-write (reflink on Btrfs / XFS / bcachefs, clonefile on APFS), the snapshot is an instant, space-free clone. Otherwise it needs roughly one file size of space: the host checks free space first and, if it is below file size + 64 MiB, fails with `insufficient-space` before sending anything; the message states how much is needed and how much is free, and the destination is confirmed unwritten. If the source directory is not writable, the snapshot falls back to the system temporary directory, with the same space check. Crash leftovers in the directory are swept before a new snapshot is created, using the same rules as download temporaries. Preparation must not masquerade as uploaded bytes. After transfer, server-side SHA-256 is preferred; pure SFTP accounts without server hashing use a streaming read-back, potentially adding roughly one file size of download traffic. Verification/commit remains running, with unknown speed/ETA rather than a false zero-second completion. The current host cannot reliably validate reconnection identity and namespace, so it explicitly returns `CanResume=false` and rejects resume; there is no automatic checkpoint retry or recovery across application restarts.

Desktop tool cards show a progress bar, transferred/total bytes, percentage, speed, ETA and stage. Unknown totals, preparation and verification use indeterminate progress; failures, cancellation and unknown outcomes are not green successes. Switching chats leaves progress on its original card. Model Stop ends model waiting while the original card can still explicitly cancel. Closing/destroying the panel, plugin deactivation, MCP session deletion/settings reload or Bridge authorization reload explicitly cleans up without claiming remote-stop confirmation. Strict run isolation remains: new model turns cannot query old-run jobs; the original card retains its scope to manage approved uploads.

Bridge pauses the remaining turn budget only during independent upload waiting without other command/monitoring jobs, then resumes the original remaining budget before model requests. That wait also gives up the bridge's global concurrency slot (the chat's own serial gate stays held); before the next model call the turn queues to take back the same gate and resumes the budget only once it has it. Host confirmation has no time limit and a large file can take hours, so holding the slot would leave other chats stuck at the gate. Pure commands/monitoring retain their existing deadlines; manual Stop and lifetime cancellation always apply. When an upload continues after model Stop, Bridge retains a local observer and sends the identified job's final state without restarting the model. Active MCP transfers are not reaped by the two-hour idle policy merely because no tools are called, while completed inactive jobs do not block idle reclamation indefinitely.

AI approval and host upload confirmation are independent layers. Before reading file content or uploading, the host confirms the source plugin, actual target session, local source, **file size**, remote path and overwrite policy for each job. Only that job is allowed; terminal/session-opening grants do not carry over and there is no Always Allow option. AI `Bypass` cannot skip host confirmation; missing gate, prompt or usable desktop window means rejection. Waiting for confirmation remains part of the independent job lifecycle, not a long RPC. Revoking permissions in plugin management cancels pending and active upload leases, which are rechecked before commit. Revocation withholds new paths/results, but cannot erase previously known inputs/history or promise rollback of a committed file. When the host explicitly denies an upload, desktop/Bridge force the current run to pause with `ExecutionDenied`, without asking the model to find an alternative path. External MCP fails only that call, not its entire fixed client run. After a stop (the panel's Stop, switching sessions, closing the panel, IM `/stop` and round time-outs) or any denial in the round (plugin approval card, host confirmation, root authentication), uploads / downloads of that round still in the `Approval` phase (model-initiated downloads included) are withdrawn too: those queued behind the confirmation gate are dropped with the cancellation, a confirmation already shown closes, and they end `Cancelled` with nothing written; a start receipt that arrives after the stop is withdrawn as soon as it lands (since 2026-10-25). When the host advertises `SupportsTransferWithdraw`, each one goes through conditional withdrawal, `WithdrawPendingTransferAsync` (SDK 2.1.4, since 2026-10-31): the host decides "still awaiting confirmation?" and withdraws in one step, so an approval landing at the moment of the stop answers `PastApproval` and keeps going, and a plugin snapshot that is a beat behind cannot withdraw the wrong one; every outcome only publishes the host's snapshot and never falls back to an unconditional cancel. Hosts without it keep the old path — fetch the latest snapshot and cancel by generation only while it is still in `Approval` — with a one-round-trip gap in between (see [SDK §3.3f](../sdk/sdk-reference.md#33f-conditional-withdrawal-sdk-214)). Approved transfers finish as usual, a round that ends normally withdraws nothing, and a single denial on an external MCP connection does not withdraw anything either. If host revocation withholds access to results, pause safely with withheld/`Unknown` rather than repeatedly rereading it as a transient network error. This is a dedicated enforcement point for the new upload API, not a claim that other file capabilities or the universal `remote.files`/local-file Broker are implemented. See [SDK §3.3b](../sdk/sdk-reference.md#33b-independent-upload-jobs-sdk-211) and [IPC §7.2](05-ipc-protocol.md#72-independent-upload-jobs-sdk-211) for protocol and state definitions.

### 1.7 Dual-entry background AI downloads (SDK 2.1.2)

**The download contract is officially published in SDK 2.1.2 on NuGet.org.** Host src / tests central packages, the explicit AI package reference and `minSdkVersion` have all moved to 2.1.2 (`apiLevel: 2`), without local packages or temporary feeds. Downloads are available on Windows and Linux / macOS (x64, arm64) hosts: the commit tests have actually run on Windows and Linux (on ext4 and tmpfs under WSL Debian), macOS only through CI; a real SSH / GUI end-to-end flow is still not claimed as validated.

- **Model entry:** `download_remote_file` removes its former 32 MiB check and starts a background `StartDownloadAsync`. Default `overwrite=false` rejects existing destinations; explicit replacement still requires approval. A given `local_path` follows the same rule as uploads: it must be a fully qualified absolute path (on Windows, `C:foo`, `\tmp\x` and other forms the host would complete from the process's current directory are rejected) and is normalized before approval, so the approval card and host confirmation show the real destination. A structured receipt contains Download direction, state/phase, 64-bit bytes, speed, ETA, generation and stop confirmation, without waiting for the entire file.
- **Remote-link entry:** the former 64 MiB check is removed. After save-path selection, an independent scope and ordinary progress card bind to the conversation/session at click time. This is not a model tool call and fabricates neither model receipts nor terminal notices. The picker does not pre-truncate the final destination or replace per-job host approval. Choosing an existing file has the system save dialog confirm the replacement first; the host is then asked with `overwrite=true`, and its confirmation says the file will be replaced. Chat switches do not mix progress; panel close uses `CloseTransfersAsync`, including cleanup of late starts.
- Both entries share host jobs, bandwidth and resource budgets, not unlimited resources: both directions together allow four actual transfers, 32 active/queued jobs and 1024 lifetime receipts per plugin. An exhausted receipt budget or an operation-identity conflict is a refusal before the host is involved: the tool reports "rejected before execution", which is not an unknown outcome and does not stop the turn with TaskUnknown. Session authorization, model-context/small-file reads, chat attachments and IM platform file limits remain.

`transfer_status` / `transfer_wait` / `transfer_cancel` cover both directions. Short waits default to two seconds, at most 30; expiry or request cancellation ends only that wait, while downloads have no default execution deadline. Explicit cancellation targets the expected generation. Downloads have `CanResume=false`; never automatically redownload Unknown. Cards show upload/download direction, Approval/Transfer/Verification/Commit, bytes, percentage, speed, ETA and cancellation. Unknown totals never invent percentages; full bytes or verification/commit are not success. When the tool got no snapshot (refused, stopped before starting, receipt lost) the card shows a warning instead of a completion check. `Succeeded` requires confirmed final commit. Unknown/TimedOut without stop confirmation does not mean side effects ended; uncooperative backends retain slots/handles until actual exit. The stop grace period is the same as for uploads, 30 seconds.

Local observers refresh progress without a model request or context message for every frame. After three consecutive observation failures only that job is reported as "progress cannot be confirmed" (an unknown outcome); the observer then backs off from 1 second, doubling up to 30 seconds, and keeps watching until the host's terminal state, revocation or plugin deactivation, withdrawing the uncertainty as soon as it gets a fresh snapshot. The coordinator delivers each job's terminal notification only once; status/wait consuming it prevents duplicate notices. `transfer_resume` only looks at the original job and does not consume its terminal state, so when it cannot resume, the completion notification still delivers that state to the model. There is never a second tool result for the original CallId. Paths/errors remain untrusted data, and strict owner/run isolation remains. Stop ends model waiting, leaving the job/local observer running and its original card able to cancel explicitly. Panel close/destruction, plugin deactivation, MCP session deletion/settings reload and Bridge authorization reload explicitly clean up. Bridge retains transfer-only remaining-budget suspension, release of the global concurrency slot (see §1.6) and post-Stop local observation/final reporting without automatically restarting the model; command/monitoring budgets are not expanded. External MCP must explicitly query status/wait, with no server-driven model-wakeup promise; active transfers remain protected from idle reclamation.

Download host permission is separate from upload/terminal/session-opening permission, confirming plugin, actual session, remote source, final local destination and overwrite policy for every job. AI Bypass cannot skip it; missing prompt/window means rejection. Revocation cancels pending/active leases, rechecks before commit and redacts subsequent metadata, while cleanup cancellation remains available; committed files are not rolled back. `send_file` refuses registered download destinations before successful commit, rather than sending an old same-name file, and checks both before and after approval: a file whose size or modification time changed during approval is not sent; existing directory restrictions, outbound approval and IM platform limits remain.

**Safe commit supports Windows fixed local NTFS and local filesystems on Linux / macOS (x64, arm64):** the destination directory chain is pinned before approval (Windows holds every ancestor's handle without delete sharing; Linux / macOS walk from `/` with non-following `openat` calls and keep only the parent directory fd), a random temporary file is created exclusively, and the commit is atomic relative to the pinned parent, so renaming an ancestor afterwards cannot redirect it. Default no-replace and approved overwrite never delete the destination first; timestamp preferences target the owned temporary handle. UNC, 9p / SMB / FUSE / NFS and other filesystems fail explicitly before approval, and unsupported backends fail explicitly too; neither falls back to directly writing the final path. Count actual local writes; check length, before/after metadata and available digests, without requiring exec or a second full download for pure SFTP. This is not an atomic remote snapshot guarantee. See [SDK §3.3c](../sdk/sdk-reference.md#33c-independent-download-jobs-sdk-212), [Capability APIs §2.2](07-capability-apis.md#22-independent-download-jobs-sdk-212) and [Security §1.2](12-security-threat-model.md#12-actual-background-download-security-boundaries-sdk-212).

### 1.8 AI plugin provider credentials and failover (2026-10-25)

1. **Credentials do not follow a changed address.** When a provider's Base URL moves to another origin (a different scheme, host or effective port; changing only the path or case, or spelling out the default port, does not count), a separate confirmation appears before saving (no longer the same button clicked twice;
   an overlay with a card inside the plugin view, default focus on "Cancel", Esc cancels, Tab cycles inside the card, clicking the overlay is not a choice):
   - Providers with keys: the primary slot, the extra slots and the own keys of models without an override address are cleared (the card names those models), and the extra and current slots reset; a key entered in the same save goes into the primary slot. The button reads "Remove and save";
     cancelling says "Cancelled. Nothing was changed." in the status line and keeps the draft.
   - Subscription providers (custom OAuth, Azure and the like): sign out (delete the token, advance the sign-in generation) and likewise clear the models' own keys that follow the old address; the card says that chats and IM bots using this provider will be interrupted.
     The button reads "Sign out and save"; afterwards sign in again for the new address under "Manage sign-in". Requests in flight are refused when re-checked; the one already on the wire still goes to the old address with the old address's token (nothing leaks, that round is just void).
   - If what is to be cleared changes after confirming (another key saved elsewhere, a slot's value replaced, another sign-in), the commit refuses and asks again with different wording, so nothing the card did not list is cleared.
   - While the address change is unsaved, "Test" carries no stored key or sign-in: a key provider sends only a key newly typed into the form; a subscription provider that is still signed in asks the user to save first and test after signing in at the new address.
   - The catalog page shows no address box for fully configured subscription rows; the address is changed only on the settings page.
2. **A model override on another origin must bring its own key**: for a model whose override base address has a different origin from the provider, none of the provider's keys (primary or extra slots) go along; to send a key, tick "Use a separate API Key for this model".
   It used to borrow Key 1 across origins — after a provider moved, the new primary key entered for the new address was sent to the old override address. The provider page names such models, and the model page explains that requests go without a key
   and offers "Use the provider's Key 1 here" (ticks the own-key box and fills the primary slot's current key into the form; it takes effect on Save). Subscription providers are outside this rule (the issuer decides where a token applies).
   When the provider's own address has no parseable origin (empty or mistyped), only the primary slot is used as before. Moving a model's override address to another origin still takes the model's own key along (left open).
3. **Anthropic environment variables only for the official host**: when the Anthropic protocol has no key (the provider has none, a model ticked its own key but left it empty, or the key was cleared by an origin change and not yet replaced), the local `ANTHROPIC_API_KEY` / `ANTHROPIC_AUTH_TOKEN` are used only for `https://api.anthropic.com` (default port;
   case, a trailing slash and `/v1` are normalized) — configuring only the environment variables to reach the official API still works, and with both set the SDK takes the former;
   for any other address both are explicitly set to null and nothing is sent (plain http, another port, or another host carrying the official name are not official).
4. **Failover candidates**: when the chain is empty (or holds only deleted models), endpoints of the same catalog and model are discovered automatically, but **by default only within the same provider instance and the same credentials** (the same model over another protocol or address);
   to switch to other accounts of the same catalog (another instance, or a model's own key — say, a company and a personal Copilot), tick "When the list is empty, also switch to another account of the same catalog" in the "Failover" section of the global settings
   (`AiSettings.AutoFailoverAcrossAccounts`, off by default; the whole conversation then goes to that account and is billed to it). Entries placed in the chain explicitly are not affected by the switch. Existing configurations are off after upgrading.
5. **Cooldown**: a key answering 401 (the key itself rejected) cools down as a whole for 60 seconds and is avoided for every model; 403 / 429 cools down only "this key used for this model", so sibling models under the same key are still probed during failover.
   Success on any model clears the whole-key cooldown; a cooldown for one model clears only on success with that model. The "cooling down" on the settings page's key rows reflects only the whole key.
6. **Empty primary slot**: when Key 1 is removed (only the primary slot's secret is cleared) while extra slots remain, the list still shows an empty "Key 1" ("(empty — use the pencil to fill it in)") that cannot be shown, removed or tested; the pencil fills it and Save puts it back into the primary slot;
   "Test all" tests only rows with a key.
7. **Switch notice card** (2026-10-31): when failover moves to another endpoint, or the same model moves to another key, that reply gets a "Provider switched" card right below its header — the first line reads "Now using provider·model" (when the provider has more than one key it also names "Key N · ●●●●last four", written as on the settings page's key rows; the key itself never appears),
   and the lines below give "endpoint: why" for each hop (rate limited / authentication failed or access denied / timed out / server error or overloaded / could not connect / empty reply / connection settings changed, plus the HTTP status when the server returned one; the same classification that decides switching);
   when the turn finishes and the switch sticks (the selection still points at the endpoint that answered, or the same model's new key has become the current slot with rotation off) it adds "later requests also go here, and are billed here".
   Several switches in one turn update the same card (beyond 4 hops: the first, a count of the middle ones, the last two); candidates already skipped at the probe stage are not hops. A turn that did not finish keeps the card, without the "later requests" line.
   **It never enters the model context**: the card lives only in the UI — the message history sent to the model, "copy reply" and the stored reply text never contain it; it is saved in the reply's metadata (`Switch` in `chat_meta`; keys only as ordinal and last four),
   restored as a card when the conversation is reopened while the context is still built from the reply text alone, and exported to Markdown as a quote. Chat panel only (the IM bridge has no failover).

The only new global setting is `AutoFailoverAcrossAccounts` (global settings → Failover, off by default, applied on Save).

**Model not available for this account** (2026-11-16): 400 / 404 responses whose error code or message names the model (such as `model_not_found` from Codex with a ChatGPT account) are recognized by `TransientFailure.IsModelUnavailable`; a bare 404 (usually a wrong Base URL path) and ordinary 400 parameter errors are not. The condition depends only on "account + model", so it is handled like a 403: other keys of the provider are tried first and only that key-for-this-model is cooled; with an empty chain, automatic discovery appends **other chat models of the same provider instance and credential** after same-model connections (in configured order; same account, so billing and data recipient do not change, and `AutoFailoverAcrossAccounts` does not apply); a configured chain is still followed. The switch card reason reads "model not available for this account". Subtasks and team members: see the delegation paragraph in §1.4 — with no output and no tool calls yet they are rerun on the parent model and then other delegation candidates, and the model is marked unavailable for the turn; after tool calls they are not rerun.

Supported levels depend on the server and model.

Thinking effort remains a conversation-local override: it does not update saved model configuration, selecting the saved level clears it, and switching models clears it. Models explicitly marked as unable to reason cannot adjust it; unknown catalog capability still permits trying. After settings updates, model deletion or failover, the entry and thinking display follow the actual selected model. This layout does not add voice input.

### 1.12 Grouping and displaying tool calls (2026-11-16)

An Agent turn often makes dozens of tool calls. Previously each call got its own card, stretching the reply into a long column with the conclusion buried at the bottom. Grouping only changes where cards sit in the visual tree; the cards themselves are still created, stored and replayed one by one:

- **Tool groups**: adjacent tool cards join one group. The group header shows "Ran N actions", the three most frequent tools (`run_command ×9`) and the number of failed / denied / invalid-argument calls (with a warning icon). While running, the two most recent cards stay visible; the group is sealed when the model starts writing, an approval or notice card is inserted, or the turn ends, after which an unexpanded group is a single line. A group with only one card shows no header. Transfer cards keep their progress bar and Cancel button and are never grouped.
- **Work log fold**: when a turn ends with at least two tool calls and a written conclusion, the thinking, tool groups and in-between text move into a collapsed "Work log · N actions · duration" line; subagent groups, team cards, approval cards and images are not folded. Turns that were stopped, failed or ended without a conclusion are not folded.
- **Readable form**: expanded details parse argument and result JSON and lay it out as "key: value" lines, multi-line strings as real lines and nesting indented by two spaces, with no `<`-style escapes. The header summary prefers the main argument (command / path / url). Non-JSON text is shown as is.
- **Encoding sent to the model**: tool results and background completion notifications use an encoder that allows every Unicode range (`JavaScriptEncoder.Create(UnicodeRanges.All)`), so Chinese text is no longer sent as `\uXXXX`. `< > & ' +` are still escaped, so §1.4's guarantee that output cannot forge `</untrusted-command-output>` is unchanged; this is why UnsafeRelaxed cannot be used. Stored arguments use relaxed encoding for display and history only.
- **History**: up to 200 tool calls per turn are stored (previously 12), with arguments and results sharing a 160K-character budget per turn (512–4K each).

### 1.13 In-run context management and resuming interrupted runs (2026-11-16)

§1.4's automatic batch continuation lets a turn run any number of steps, but context compaction used to run only once, before the user's message was sent. Within a turn every step carried every tool output, so a few dozen steps exceeded the window, the provider rejected the request and the turn ended.

**In-run compaction** (`RunContextCompactor`) sits inside `RecoveringChatClient` and outside the steering channel. Before every model request it acts in stages on usage relative to "window − output reserve", following Claude Code's microcompact and autocompact:

| Usage | Action |
| --- | --- |
| ≥ 50% | Older large tool outputs become a one-line placeholder; calls and arguments stay, and the 12 most recent outputs are untouched |
| ≥ 70% | Only the 4 most recent tool outputs are kept |
| ≥ 85% | Earlier steps of the turn are written up by the model as a progress summary (including tool arguments, up to 1500 tokens) attached to the turn's opening user message; cuts land only at the start of a step and at least the last 2 steps stay verbatim |

Original messages are never modified: the function loop and checkpoint keep the full list, and each request rebuilds the outgoing version from recorded state. State only grows, so the same prefix produces the same result between compactions and prompt caching still hits. Messages are recognized by call id or "role + text", not by object reference (batch continuation rebuilds message objects). The turn's opening prefix (system prompt, history and this user message) is not touched. Estimates are character-based and are only calibrated upward (1.0–2.5×) once the provider reports real input usage. If writing the summary fails, only clearing is done. Each pass leaves a divider in the reply stating how much was cleared and how usage changed. Desktop and the IM bridge both use it; it follows the "Context compression" switch and does nothing when the model window is unknown.

**Resuming**: history stores only reply text; tool calls, results and background notifications live in memory, so a turn's progress was lost when the app exited. In Agent mode `AgentExecution` raises a progress event for every completed step, tool result or background notification, and the panel writes a checkpoint at most every 1.5 seconds to `run-checkpoints/<conversation id>.json` in the plugin data folder (temporary file then replace; each result clipped to 6K, at most 600 messages; only filename-safe characters in the name). It is deleted on normal completion. When a turn is stopped or fails, a final copy is written and a resume card appears at the end of the reply; loading a conversation that has a checkpoint shows the same card. "Continue" starts a new turn with a new user message: the most recent 24 messages go back verbatim (starting at the beginning of a step), earlier ones are described by the progress summary and a list of calls, and every call that had no result when the run stopped gets "outcome unknown; check the current state before deciding whether to redo it". This matches §1.4's rule that recovery covers model steps, not side effects: nothing is replayed. Background commands still running remotely are not reattached: the resume instructions list `run_command` calls in the checkpoint that reported "running" with no later final state (session, command, last known state) and ask the model to verify before deciding. Deleting a conversation, clearing history or truncating also deletes the checkpoint; a deleted conversation is not written again in this process (if it was running, its shutdown does not write one), and clearing records the time and drops writes from runs that started before it; timed writes and the deletion at normal completion share one lock. The IM bridge writes checkpoints in Agent mode too (keyed by `bridge-` plus the chat key, stable across restarts), suggests `/continue` after a stop, timeout or failure; `/continue` restores the steps (after a restart, the original request first) and starts a turn, and `/new` discards the old checkpoint. Subagent and team member tasks use in-run compaction as well (the prefix is the system prompt and task instructions), following the "Context compression" switch.

### 1.14 Team mode (2026-11-16)

After a team starts or retries, the desktop and IM coordinators wait for the consolidated report before sending the next lead-model request. Other task results that arrive during this wait accompany the report. Stopping the turn cancels the wait. A steering message reaches the lead on its next request and keeps its place as subsequent tool steps are added.

`delegate_subagent` suits a few independent subtasks. When several roles must hand work to each other (investigate → change → review), the main model calls `team_run(goal, members[], tasks[], timeoutSeconds?)` once. Whether to form a team is decided adaptively by the main model, without the user having to ask: when `team_run` is exposed in the turn, the system prompt adds a section of team criteria (three or more steps needing different expertise, later steps depending on earlier findings, investigations that can run in parallel and be combined, changes or security conclusions that need an independent review — a team is preferred when two of these hold; questions answerable in a few tool calls, single-file edits and command-heavy work do not get a team; usually 2–4 members). It is not added when the tool is disabled or on external MCP. The design follows Claude Code agent teams (shared task list and mailbox) and MiniMax Mavis (engine-driven scheduling with a Worker / Verifier rework loop).

- **Definition**: up to 16 members and 32 tasks (raised from 6 / 12 on 2026-11-19; these are only safety limits against a runaway plan — the main model sizes the team from the scope of the work, one member per distinct responsibility, usually 2–4 for small tasks and more for large projects spanning many areas; at most 4 run at a time under the orchestrator's concurrency limit, and every plan is confirmed by the user before it starts). Members have a name, role, optional model and `allowWrites`; tasks have an assignee, `dependsOn` and optional `verifies`. Names are unique and `lead` / `all` are reserved; dependencies and review targets must exist and may not refer to themselves or form a cycle. If validation fails, nothing starts.
- **`TeamEngine` schedules, not model polling**: a task starts only when its dependencies have completed, a member runs one task at a time, and when a dependency fails, is cancelled or is blocked, downstream tasks are marked blocked. Each task is a managed subtask on `SubagentOrchestrator`, reusing its concurrency of 4, approvals, serial file-mutation lock and run cards; managed entries do not wake the main model one by one. Each task defaults to 600 seconds (30–1800) and up to 60 steps; the orchestrator's total limit is raised to "tasks × 2".
- **Information flow**: upstream reports are attached to downstream task instructions as `<upstream-results>`; summaries of a member's earlier finished tasks are attached to its later ones. Members have `team_message` (to a teammate / `lead` / `all`) and `team_board` (the board and finished reports). Running members receive messages before their next step through an inbox client (like the steering channel, delivered messages are resent every step); idle members receive them with their next task's instructions. Messages and upstream reports are written by other models and are framed as data for the receiving member.
- **Review loop**: a review task ends with `VERDICT: PASS` / `VERDICT: FAIL`, and a missing verdict counts as FAIL. On FAIL the reviewed task is sent back once with the review feedback and then reviewed again.
- **Re-runs after errors and reassignment (2026-11-17)**: when a member's run fails, the orchestrator uses `TransientFailure.IsRetryableRun` to decide whether running it again unchanged could succeed, and records the answer in `SubagentSnapshot.Retryable`. Retryable failures are transient ones (network errors, 408 / 429 / 5xx, overload) and errors whose text says the stream was cut upstream (for example a relay's "Upstream response stream was interrupted": an error frame inside the stream surfaces as an exception without a status code, which request-level retries do not handle). Other 4xx answers from the server, refusals or output limits, pauses caused by an unknown command result, and cancellation are not retried. The engine re-runs a retryable failure automatically, up to 2 times per task (`MaxAutoRetries`), and downstream tasks are not blocked meanwhile; only when those are used up is the task recorded as failed and its dependents blocked. It can still be re-run by hand after that: the main model's `team_retry(taskId, assignee?)`, or **Retry** / **Hand over to** in the team console's task drawer, both of which call `TeamEngine.Retry`. Failed, timed-out and cancelled tasks go back to pending; retrying a blocked task re-runs the upstream tasks that blocked it; the task can be handed to another member; blocked dependents become pending again, a team that had already finished is reopened, and a new consolidated report is delivered once everything has settled (a report that is not fully completed carries a `recovery` field pointing at this). A re-run is a fresh run whose instructions gain a `## Retry` section: what stopped the previous attempt, what it had written, and an instruction to check which changes already took effect before continuing. Re-runs after errors do not use the rework allowance (reworks are counted separately in `Reworks`), and `TeamTaskInfo.Retries` holds the re-run count. Manual retry is only available while the turn is running: the engine is released with the orchestrator when the turn ends.
- **Choosing a model per task (2026-11-17)**: the main model sets each member's model in `team_run`'s `members[].modelId`; candidates are still limited to the chat models of the current provider instance, and omitting it inherits the main model's model. Previously the main model was given only ids and names, while the system prompt told it to inherit the parent unless there was a supported reason and not to infer capability from names, so in practice the whole team ran on the main model's model. `SubagentRunner.ModelCatalog` now attaches the facts known from configuration to every candidate: `contextTokens`, `maxOutputTokens`, `inputPricePerMTok` / `outputPricePerMTok`, `reasoning`, and `parent` on the model the main model itself runs on. Missing facts are left out (no price entered, a context window that is only the default used when the real one could not be fetched, unknown reasoning support). The catalog reaches the `team_run` and `delegate_subagent` tool descriptions through `SubagentOrchestrator.ModelCatalog` (the same on desktop, the IM bridge and external MCP). `TeamGuidance` and `DelegationGuidance` require assignments to be based on those facts only, never on model names: a cheaper model for routine collecting and summarising, a large context window for heavy reading, a reasoning-capable or higher-priced model for design, hard debugging and important changes, and preferably a different model for a reviewer than for the member it reviews, so the check is independent; with a single candidate or indistinguishable facts the main model's model is inherited. Explicit user choices always win. The plan confirmation (`DescribePlan`) shows each member's model by name instead of its configuration id.
- **Cross-provider assignment (2026-11-18)**: candidates were widened from "the current provider instance" to the chat models of **every** provider instance the user added (`SubagentRunner.ModelChoices`, the parent model's provider first, image models excluded), so the main model can put members on whichever vendor's model suits their work. Each catalog entry also carries `provider` (provider instance name) and `model` (real model id). `TeamGuidance` and `DelegationGuidance` share `ModelSelectionGuidance`: assign by the facts above first; when a model id clearly identifies a well-known vendor model, the main model may use what it knows about that model's strengths (coding, long documents, multilingual writing, math, tool use); unrecognised names (gateway aliases, custom names) count as unknown, and the listed facts win when they disagree; a reviewer preferably gets a different model from the author, ideally from another provider; providers are not switched just for variety — each bills separately and receives whatever its subtasks read. Fallback is widened accordingly to `CannotUseModel`: besides an unavailable model, 401 / 403 / 429 and OAuth refresh failures also rerun on the parent model while there is no output and no tool call, so one provider's expired key does not fail the whole member. This entry supersedes the "never by model name" rule above.
- **Consolidation**: when everything has finished, one report (each task's status, reworks, verdict and report, plus messages to the lead) goes back to the main model through the same `<untrusted-subagent-results>` notification as subagent results. The orchestrator counts the team when deciding whether work is still in flight, so gaps while waiting for dependencies or reworks do not end the turn early. The main model also has `team_status`, `team_message` and `team_cancel`.
- **Permissions**: members match subagents: read-only by default, `allowWrites` must be explicit, and changes go through the parent turn's approvals and serial lock. `allowCommands` (off by default) adds `run_command` and `task_status` / `task_wait` / `task_cancel`; every command is approved through the parent toolbox under the approval level with the card naming its origin, a denial stops the turn, and multi-host runs, terminal input, sessions and transfers stay unavailable. `team_status` (for the lead) is removed from subtask tools. `delegate_subagent` gains `allowCommands` too.
- **Plan confirmation before launch**: `team_run` validates first, then `ConfirmPlanAsync` shows a "Starts a team" approval card through the same approval handler (`DescribePlan`: goal, members with ✎ / >_, tasks with ← dependencies and ⟲ review). The bypass level skips it and "always allow in this session" is offered. A denial is **not** a stop boundary for the turn; it only tells the main model the user declined this plan. In IM it arrives as an approval message.
- **UI (2026-11-17: entry card + team console)**: the conversation keeps only a two-line entry card (`TeamEntryCard` in `ChatPanelView.Team.cs`): the goal and a phase chip, then the member avatars (identity colors use the host-forwarded `VelaShellCyan` / `Blue` / `Magenta` / `Yellow` / `Green` and their `Dim` variants, kept separate from status colors) with "done / total tasks · running · elapsed · team tokens ≈total estimated cost". The whole card is clickable (Enter / Space when focused does the same) and opens `TeamConsoleView` through `Ui.ShowPanelAsync` (`PanelDisplayMode.Document` + `PanelPlacement.Tabs`) as a document tab in the main window's tab group, titled "Team · goal" (the goal flattened to one line and cut at 24 characters). Tabs are keyed by team id, so an open one is only activated; if opening fails it falls back to a separate window (the same fallback as diff documents).
  - **Data**: the entry card and the console share one `TeamConsoleSession` (the latest `TeamBoardSnapshot`, the `SubagentSnapshot` of every team task run, the cancel hook and the `TeamTelemetry` usage series). `AssistantBubble.UpdateTeam` pushes every refresh into it; the console subscribes to `Changed` and repaints on a 700 ms coalescing timer (immediately when the message count changes). While it is not in the visual tree it does not subscribe and its animation clock is stopped. After the turn ends it stays on the last snapshot; a team opened from history is a static final state.
  - **Snapshot fields added for the console**: `TeamTaskInfo.StartOffset` (how long after the team started the task started — where its bar begins on the timeline), `TeamMessageInfo.TaskId` (the task a message is about) and `TeamBoardSnapshot.LeadModelId`. The engine also records two UI-only message kinds: `handoff` (when a task starts, each upstream report written by another member is handed to it; linked to the upstream task) and `review` (a review verdict, linked to the review task; the former rework `peer` message is now this kind). None of this enters the model context. `chat_meta` additionally stores `CachedInputTokens` and `ContextTokens` per subtask so cost and context usage are right when a team is opened from history.
  - **Page** (`TeamConsoleView` with `.Panels` / `.Graph` / `.Drawer`; derivations are pure functions in `TeamConsoleModel`): header (phase, goal, run time) → six stats → team topology and data flow | members → task timeline | token usage → communication log, side by side in two columns when the content area is at least 1150 px wide. Relations come from the plan: the lead assigns every member, a dependency is a handoff, `verifies` is a review, and `peer` messages between members are a collaboration (one line per pair). Members are ordered by dependency depth, at most three per row, and the lead is placed where the fewest of its straight lines are blocked; a blocked line picks a curvature that clears the node, and labels avoid nodes and each other. A node's outer ring is its context usage (latest request input ÷ model window) and its state comes from the running task's `Activity` (calling a tool = working, no tool = thinking, waiting for approval / a file lock / dependencies = waiting, a failure = blocked). A new message sends dots along the matching line. A running task has no trustworthy completion figure, so the timeline shows time spent instead of a percentage. The token rate samples each member's increase every 2.5 seconds and is only recorded while the team runs.
  - **Detail drawer**: a member (usage, cache hit rate, context usage, tools used, tasks owned, who it talks to), a task (owner, reviewer, upstream tasks, the report — appended as it streams while running, with a Cancel button) and the conversation between two parties (Report / Review / Handoff messages carry the matching report, tools and that run's usage). The three link to each other, the path is kept as a back stack, and Esc or the scrim closes it. When a task did not finish (failed / blocked) and the turn is still running, the task page shows **Retry** and **Hand over to**. The drawer and the scrim stay in the visual tree; when closed the drawer rests beyond the right edge of the page and the scrim is transparent and ignores pointer input. Opening and closing only change the target values of `RenderTransform` and `Opacity`, so the transition always starts from the current position (moving the drawer to a start position first and back on the next tick makes both steps animate, which shows as a flash on open).
  - **Styling**: the page is a standalone document outside the chat panel's resource scope, so it merges `AiTheme.axaml`, LiveMarkdown's styles with `MarkdownSkin.axaml` (extracted from `ChatPanelView.axaml` and shared by both; the keys that have to be overridden, such as code block backgrounds, are in `MarkdownSkin.Sync`) and `TeamConsoleStyles.axaml` itself. Every color is bound to a `Vela*` token; the four surface levels are `VelaBgPage` → `VelaBgSidebar` → `VelaBgInput` → `VelaBgHover`, which keep their order in both the dark and light themes. Member avatars (`TeamAvatar`) are vector-drawn robots whose identity color, eyes and accessory rotate with the member index.
  - Cost uses each run's own model prices with cached input at the cache price. When the orchestrator is released at the end of a turn, only a team that has not finished is recorded as cancelled. Team tasks are not repeated in the subagent group. The board is stored in `ChatTurnMeta.Team`, with reports and messages clipped and unfinished tasks stored as cancelled.

### 1.15 Token-saving file tools and change diffs (2026-11-16)

File reads used to return the whole file, there was no content search tool at all, and changing several places in one file took one patch call each, so the model pulled back a whole file just to look at a few dozen lines.

- **Ranged reads**: `read_local_file` / `read_remote_file` gain `offset` (first line, 1-based) and `limit` (default and maximum 2000 lines). Output is `line\tcontent`; a truncated read states the total line count and the next `offset`. The tool description tells the model not to copy the line-number prefix into `oldText` / `content`. Local reads stream line by line, and the size limit now only caps the returned text; remote reads use the sequential `IRemoteFs.OpenReadAsync` stream that SDK 2.2.0 already provides, falling back to `ReadAllBytesAsync` (still 256 KB) if the stream cannot be opened. Files containing NUL are refused as binary.
- **Content search (read-only, no approval)**: `search_local_files(pattern, isRegex, path, glob, contextLines, maxMatches, ignoreCase, workspaceId)` returns `relative/path:line: content`, skips binary files, files over 16 MB and folders such as `.git` / `node_modules` / `bin` / `obj`, never follows symbolic links or junctions, checks the starting path through `LocalPathScope` as usual, and times out a single regex match after 1 second. `find_local_files` finds files with `*` / `**` / `?` / `{a,b}`. `search_remote_files` runs a `grep -rnIsH` command **assembled by the tool itself**: every model-supplied value is single-quoted as a whole, the pattern goes through `-e` and the path after `--`, so it cannot form a second command or forge options, and it can read nothing beyond what the approval-free `read_remote_file` already can. It therefore needs no approval. It times out after 30 seconds (the remote grep process is not guaranteed to exit with it) and assumes a POSIX shell on the server.
- **Multiple edits**: `patch_local_file` / `patch_remote_file` gain `replaceAll` and `edits[{oldText, newText, replaceAll}]`, applied in order; if any edit does not match, nothing is written, and one call needs one approval. The old parameter names are kept, so history replay is unaffected.
- **Change events**: `AgentToolbox.FileChanged` (`Action<FileChange>`) fires synchronously after a successful local or remote write, patch, file delete or file rename, carrying the full text before and after (null when over the size limit or not UTF-8). `Location` is `local:<workspaceId>` / `remote:<sessionId>`. Directory operations raise no event, subscriber exceptions do not affect the tool result, and subagent toolboxes reuse the parent's subscriber.
- **UI**: tool cards show an icon per category (`ToolIcons` maps exact tool names; MCP and other external tools get a plug), and the status icon moved to the right. File-editing cards show `+N −M` in the header and expand into a unified diff computed by the plugin's Myers line diff (`LineDiff`), with line numbers, colored additions and removals, and 3 lines of context. The added/removed backgrounds are the theme tokens `VelaStatusConnected` / `VelaError` at low opacity, so they follow all 12 named themes without new tokens. A "N files changed" bar above the input box collects the conversation's `FileChange` events (merged per file: Before from the first change, After from the last). Clicking a file opens a diff document in the main window's tab area through `IUiApi.ShowPanelAsync` (`PanelDisplayMode.Document`): side by side by default, switchable to inline, with previous/next-change navigation; an open tab for the same file is reused and refreshed in place, and a separate window is used if the tab cannot be opened. The list is per conversation and is not stored in history.
- **Second round (2026-11-17)**:
  - **Host routing**: the host used to send every Document request from the AI plugin to the dedicated region, so a diff tab could not open while the chat panel was there and fell back to a small window. Now only requests with `Placement = Right` go to the region, and only while it is empty; see [`08-ui-extensions.md`](08-ui-extensions.md). Before opening a new diff tab the plugin activates an open one, so the new tab lands in the same group; the fallback window takes 90% of the work area.
  - **Syntax highlighting**: `TextMateHighlighter` uses TextMateSharp from the plugin directory and the same themes as chat code blocks (DarkPlus / LightPlus). It tokenizes the complete old and new texts line by line, carrying state from line to line, with limits on line count, line length and time; past them it falls back to plain text.
  - **Editing**: the right pane highlights the current line and indents new C# lines to match the surrounding block. After a 300 ms typing pause, the editor compares a snapshot in the background. Paired replacement lines highlight the changed character range. Toggle `␠` in either comparison mode to ignore leading and trailing whitespace in counts, highlighting and navigation. Saving writes the edited text, including whitespace.
  - **Reviewing changes**: open a pending diff to keep or discard the AI change. Editing the right pane switches the actions to saving or reverting your draft. Above the chat input, choose Keep all or Discard all. Discard all asks for confirmation. Files with external changes, unsaved drafts or incomplete restore information stay in the list with an explanation.
  - **Reading context**: in a tool card or inline diff tab, click the unchanged-line count to expand or collapse that section. Previous/next-change navigation follows the visible rows.
  - **Saving**: `FileTextStore` first reads the current file (local paths through `LocalPathScope`; remote files only after checking the session is still connected). If the content differs from the baseline, the user chooses overwrite / reload / cancel. Writes keep the BOM and use the file's dominant line ending, and do not go through agent approval. A fragment-only diff offers "Load full file", which rebuilds the old content by applying the patch in reverse.
  - **Limit**: the SDK has no before-close hook, so closing a tab with unsaved changes is not intercepted.

### 1.16 "You should know" bar (2026-11-18)

In a long reply, the part the user must not miss is often one or two sentences, and it is gone once the reply scrolls away. The desktop panel adds a "You should know (N)" bar above the input box (above the changed-files bar) holding the notes the main model pins.

- **Pinned by the main model, no separate extraction pass**: in Agent and Plan modes the desktop panel gives the main model an extra `note_for_user(kind, title, detail?)` tool, where `kind` is `warning` (a risk), `action` (something the user has to do themselves) or `info` (a finding that affects later decisions). The main model has already read the whole context, so pinning costs no extra request and sends the conversation to no one else; the trade-off is that it depends on the model following the tool description, which asks for few notes, no progress updates or answer summaries, and about three per reply at most. It has no side effects, so Plan mode gets it too.
- **Data**: one `ConversationNotes` per conversation; the same title (case-insensitive) updates in place, at most 20 notes, titles clipped at 120 and details at 600 characters. Nothing extra is stored: the tool call and its arguments are already saved with the reply and the notes are rebuilt from them when a conversation is loaded; dismissing lasts only while the conversation stays open.
- **UI**: collapsible (expanded by default), an icon and semantic color per kind, dismissible one by one or all at once; no tool card is shown for the tool in the reply. The bar is cleared or switched along with new, switched or loaded conversations.
- **Scope**: Chat mode offers no tools; the IM bridge and the external MCP server have no bar and do not get the tool. It is registered in the built-in tool catalog (read-only) so it can be disabled under "Configure tools".

### 1.17 Skills (2026-11-18)

A skill is a set of instructions for the AI on how to do a kind of task, in a format compatible with Anthropic Agent Skills: a folder with a `SKILL.md` (a header between `---` lines with at least `name` and `description`, followed by the instructions), optionally with reference files or scripts. Design and progress are in the host repository's `ai-plan.md` §12.3.

- **Where skills come from**: the user-level `~/.velashell/skills/<name>/` (not removed when the plugin is uninstalled) and `.velashell/skills/<name>/` inside the currently selected local workspace when it allows reading; the workspace's skill wins on a name clash. Skills are rescanned every turn. A skill whose header lacks `description`, whose name is invalid (letters, digits, `-`, `_`, at most 64 characters) or whose `SKILL.md` exceeds 256 KB is skipped; skills listed in `AiSettings.DisabledSkills` are left out. The header is read line by line as `key: value` (quotes and `>` / `|` block values supported), not as full YAML.
- **Progressive disclosure**: the system prompt's `skills` section lists only names and one-line descriptions (descriptions clipped at 300 characters, at most 50 skills, workspace skills marked `(workspace)`), placed before the user's custom prompt and present only when `load_skill` is actually exposed in the turn. The model calls `load_skill(name)` for the instructions and the list of bundled files, and `read_skill_file(name, path)` for a bundled text file.
- **Safety boundary**: read-only, scripts are never executed; `read_skill_file` refuses paths leaving the skill folder, symbolic links, binary files and files over 256 KB. Skill instructions are declared unable to override the user's explicit request, the tool rules or approvals. Workspace skills come from workspace files and fall under that workspace's authorization; the manual reminds users to check a project's `.velashell/skills` before opening someone else's project.
- **Scope**: Agent and Plan modes on the desktop and the IM bridge; Chat mode and the external MCP server do not offer them. Both tools are registered in the built-in tool catalog (read-only), and unchecking `load_skill` under "Configure tools" turns skills off entirely, including slash invocation. "Configure tools" also has a "Skills" page: per-skill toggles (written to `AiSettings.DisabledSkills`), the source of each skill, the reason a skill cannot be used, and buttons to open `~/.velashell/skills` or rescan.
- **Slash invocation**: when the user sends `/skill-name request`, the copy sent to the model is expanded into "explicit invocation + `<skill>` body + request", while the UI and history keep the original line; this works in Chat mode too. The desktop lists skills in the `/` picker and in `/help`; each entry point's own built-in commands take precedence over a skill with the same name (the IM router handles `/use`, `/mode` and the like first). The two entry points share almost no built-in commands, so only the skill layer is shared rather than a unified command registry.

### 1.18 Extension packs (2026-11-18)

An extension pack bundles skills, slash commands and MCP servers into one installable unit. It is called an "extension pack" rather than a "plugin" so it is not confused with the host's plugin system. Design and progress are in the host repository's `ai-plan.md` §12.4.

- **Manifest** `velashell-extension.json`: `id` (lowercase letters, digits, `-`, `_`; also the install folder name and part of the MCP tool-name prefix), `name`, `version`, `description`, and optionally `skills` (skills folder, `skills/` by default), `commands` (`name` / `description` / `prompt`, with `{{args}}` replaced by the command arguments) and `mcpServers` (`stdio`: `command`, an `args` array, `env`, a `workingDirectory` relative to the pack; `http`: `url`, `headers`). Every field is validated; an invalid manifest rejects the whole pack with a reason.
- **Installation**: from a folder or a `.zip` (manifest at the root or inside the single top-level folder), copied into the plugin data folder `extensions/<id>/`, which is removed with the plugin. Archives are checked for paths leaving the destination (zip-slip), entry count (20,000) and unpacked size (200 MB); copying from a folder does not follow symbolic links or junctions; files are copied to a temporary folder first and then swapped in. Installing the same `id` again upgrades it.
- **Consent**: before installation the user sees the skills and commands it brings and, for every MCP server, the exact launch details (command, arguments, working directory, environment variables, address, headers); on confirmation a fingerprint of that part is stored (`AiSettings.ExtensionPacks[].ApprovedMcpFingerprint`). When the fingerprint no longer matches (an unapproved upgrade, or files changed in the install folder), that pack's MCP servers are not started while its skills and commands keep working, and the UI asks for approval again.
- **Activation**: installed, manifest readable and enabled in settings. Skills join the skills list (lowest precedence on a name clash); commands expand after built-in commands and skills with the same name; approved MCP servers become ordinary `McpServerConfig`s (id `ext-packid-name`, tool prefix `packid_name`) and reuse the existing approvals, timeouts, concurrency and lifecycle. Applies to the desktop and the IM bridge; the external MCP server is not involved.
- **Not done yet**: hooks, dependencies between packs, signature checks, an online store and automatic updates.

### 1.19 "Configure tools" window layout (2026-11-19)

The window used to be "MCP server overview on the left + one long list of groups on the right", with built-in tools, skills, extension packs and every MCP server's tools stacked on one page, which became hard to read as things were added. It now follows VS Code Copilot's customization view, with section navigation:

- **Left column**: five sections, "Extension packs", "MCP servers", "Skills", "Memory" and "Tools", each with a count (installed packs, configured servers, usable skills, saved memories, enabled tools); "Tools" opens by default.
- **Right side**: the section's title, a one-line description, a search box (filters only this section and expands matching sources) and the list; page actions (install a pack, add a server, open the skills folder, rescan) sit to the right of the title.
- **Rows**: one row per source — chevron, name and subtitle, an `enabled/total` count, row actions and a switch; expanding it shows one row per item, each with its own switch. The switch is the plugin's own `AiSwitchTheme` (a CheckBox theme, so it keeps checkbox semantics; it shows a middle state when only some items are on), with all colors from tokens.
- **"Tools" page**: built-in tools grouped by the same categories as tool cards, with a category switch for the whole category; one row per MCP server whose switch turns the server itself on or off (disconnecting it immediately), expanding to its tools, with "Refresh tools" on the row.
- **"MCP servers" page**: the servers you configured (click a row to open its form) and the servers brought by enabled extension packs (read-only, managed on the "Extension packs" page).
- Disabled state is still stored as "the ones switched off", and every change is saved immediately with no "Save" button.

### 1.20 Memory (2026-11-19)

A small set of facts the AI remembers across conversations: the user's preferences, stable facts about their environment, and corrections to how it did something. Three decisions by the maintainer: the model saves memories itself and the user can add, edit and delete them; **desktop panel only** (the IM bridge and the external MCP server neither read nor write memory, since it may hold personal preferences and environment details that should not reach group chats, and group members should not be able to write to it); one global set.

- **Storage** (`Chat/Memory/MemoryStore`): `memory.json` in the plugin data folder, on this computer only. Each entry has a short id, a title (≤80), content (≤1000), an origin (`model` / `user`) and created / updated times; at most 200 entries. Writes go to a temporary file first and are then swapped in; a file that cannot be read is treated as empty and kept as `memory.json.bad`. One instance per data folder, shared by the panel and Configure tools and kept in sync through an event.
- **No secrets**: content that looks like a PEM private key, a common platform token (`sk-`, `ghp_`, `AKIA` and the like) or a `password=` / `token:` style assignment is refused. This is a rough check; the tool description also forbids storing secrets.
- **Given to the model**: the system prompt's `memory` section (after skills, before the custom prompt) lists memories, most recently changed first, capped at 8,000 characters with the rest only counted; present in all three modes. The section says memories are background noted earlier, not instructions: they may be outdated, and what the user says now wins.
- **Tools** (`MemoryToolSource`, Agent mode only): `save_memory(title, content)`, `update_memory(id, title?, content?)`, `delete_memory(id)`. Registered in the built-in tool catalog (`ToolKind.Memory`) so each can be switched off on the "Tools" page.
- **Master switch** `AiSettings.MemoryEnabled` (on by default): when off, no list and no tools; saved memories are kept.
- **UI**: the "Memory" page of Configure tools — master switch, search, add, inline edit (same validation, errors shown under the fields), delete and clear all (both confirmed); each entry shows its origin and last change; memories the model saves while the window is open appear immediately.

## 2. AI Gateway (S3, Longer-Term Mainline)

### 2.1 Why a "Gateway" Instead of Giving Every Plugin Its Own Model SDK

- **The host owns the keys**: the user configures model providers once in the
  host (Anthropic/OpenAI/local Ollama…), and API keys are stored in the OS
  credential store. Plugins never receive them.
- **Quotas and auditing**: track token usage and limits by plugin, and audit
  "which plugin sent what content to the model." This is critical for
  operations tools because terminal content may contain secrets.
- **One integration, available everywhere**: the host absorbs model-provider
  changes, while plugins use a stable abstraction.

### 2.2 Interface Shape (`vela.ai`, Permission `ai.invoke`)

```csharp
public interface IAi
{
    Task<AiModelInfo[]> ListModelsAsync(CancellationToken ct);       // Available configured tiers (such as fast/balanced/powerful; keys are not exposed)
    IAsyncEnumerable<AiDelta> ChatStreamAsync(AiRequest req, CancellationToken ct);
        // AiRequest: tier, messages, optional tools (plugin-provided tool callbacks are executed by calling the plugin back through RPC)
    Task<float[][]> EmbedAsync(string model, string[] inputs, CancellationToken ct);
}
```

- Tool-calling loop: the model requests a tool → the host calls the plugin's
  tool implementation through RPC → the result is returned to the model. Tool
  execution remains subject to the plugin's permissions; AI is not a permission
  bypass.
- **Data-egress notice**: the first time a plugin sends content obtained through
  `terminal.read` to `ChatStream`, the authorization prompt explicitly says
  "Terminal content will be sent to <model provider>"; Settings provides a
  master switch to "Prevent all plugins from sending terminal content to AI."
- The host implementation should use the official SDK for each provider;
  local models connect through an OpenAI-compatible endpoint and are routed
  uniformly inside the gateway.

### 2.3 Convergence with Automation

An AI action ("summarize this deployment output and notify me") is a rule-engine
action that calls `ai.invoke`; an AI trigger (semantic detection of anomalous
logs) is a plugin subscribing to the terminal stream, asking the gateway for a
determination, and triggering a rule. Combining the two skeletons produces an
"intelligent operations" scenario without introducing a new mechanism.
