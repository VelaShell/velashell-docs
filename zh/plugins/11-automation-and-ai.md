# 11 · 自动化与 AI

两者都是"插件系统之上的应用层",共享同一原则:**宿主提供骨架与安全
边界,插件提供血肉**。

## 1. 自动化(S5/S6)

### 1.1 模型:规则 = 触发器 + 条件 + 动作

```text
触发器(Trigger)   会话连接成功 / 传输完成 / 定时(cron)/ 手动命令 / 插件自定义触发器
条件(Condition)   when 表达式(复用 03 §6 文法):主机匹配、时间窗、上次结果…
动作(Action)      内置动作(执行远程命令、上传/下载、发通知、写终端…)/ 插件自定义动作
```

规则本体由**宿主**持有(存储、调度、执行编排、日志),插件的参与方式
有两种,刻意分开:

1. **插件消费宿主事件自己干活**(07 §8 的 vela.events + 各能力):
   适合复杂逻辑,一切行为计入该插件的权限与审计。
2. **插件向规则引擎贡献触发器/动作**(manifest `contributes.automation`):
   用户在宿主的"自动化"页面里可视化编排,把插件能力当积木用。执行时
   宿主回调插件(`automation/evaluateTrigger`、`automation/runAction`),
   动作运行仍受该插件自身权限约束——规则引擎不放大权限。

### 1.2 安全边界

- 规则创建/修改只能由**用户在宿主 UI** 完成;插件只能"建议"规则
  (`SuggestRuleAsync` 弹确认卡片),不能静默创建——自动化 + 
  `remote.exec` 的组合杀伤力大,必须人在环。
- 每条规则显示将动用的权限汇总;含高敏动作(remote.exec/terminal.write)
  的规则首次运行前逐条确认,可勾选"此规则以后自动运行"。
- 规则运行历史(时间、触发原因、动作输出摘要、成败)持久化,失败可
  一键重跑;连续失败 N 次自动挂起规则并通知。
- cron 触发的插件唤醒走 `onSchedule` 激活事件,受"错峰 + 最小间隔
  1min"约束,防插件把宿主变成刷子。

### 1.3 内置动作(宿主自带,无需插件)

执行远程命令(exec 通道)、上传/下载文件、发通知、打开会话、写终端
(高敏)、运行本地程序(高敏,显式路径)。这让轻量自动化零插件可用,
插件负责长尾。

### 1.4 AI 插件的托管执行与恢复（SDK 2.1.0）

本节记录 AI 插件当前新增源码，与上方规则引擎、下方宿主 AI 网关的远期设计分开；不是把网关/通用权限系统宣告为已实现。

**托管命令**仅在应用运行期间保存，不做断线/重启恢复：

| 工具 | 参数与行为 |
| --- | --- |
| `run_command` | `timeoutSeconds=0` 默认无执行死线（显式值上限 86400）；`waitSeconds=2`、最大 10，仅短等窗口，到期返回 running/taskId，不杀命令；`monitoring=false`；`elevated=false` |
| `run_on_sessions` | 最多 16 个目标排入共享 4 流槽位，未开流项取消后不再启动，不直接撞宿主并发上限 |
| `task_status` | `taskId`、`cursor=0`，返回状态及增量输出 |
| `task_wait` | `taskId`、`waitSeconds=2`、最大 30、`cursor=0`；等完不代表执行死线，也不取消命令 |
| `task_cancel` | 请求取消本轮任务；清理不会因读取 scope 已撤销而被阻挡 |

状态为 Starting / AwaitingUser / Running / Succeeded / Failed / Cancelled / TimedOut / Unknown。普通结果保留 stdout、stderr、退出码、超时/截断信息；sudo 是 `combined`，保留原始换行/CR 分片而不伪造 stderr。运行后取消无法确认远端停止时为 Unknown，`cancellationRequested=true`、`remoteStopConfirmed=false`；两种例外记为 Cancelled（同样 `remoteStopConfirmed=false`，但不暂停本轮）：提权命令还停在审批/认证阶段、用户命令尚未报告启动时被取消，以及显式监控任务被 `task_cancel` 点名取消（这是结束它的正常方式；随整轮 Stop 连带取消仍为 Unknown）。未开流取消为 Cancelled 且已确认未启动。SSH 断线、sudo Exited 缺退出码等为 Unknown；已启动 TimedOut 且无停止确认也阻断本 run 后续自动工具副作用，绝不由框架重跑。认证取消/失败/不支持明确表示用户命令未启动，不自动降级普通执行。

每 run 同时保留最多 128 个任务；满额时回收已收尾且终态已交付的任务，Unknown 与未确认停止的 TimedOut 不回收（它们是本轮的停止边界）。输出是线程安全有界队列（32K 字符、256 条、每条最多 4096 字符；超长的一段按序拆成多条，不截断），用 `NextCursor` / `EarliestCursor` / `OutputTruncated` 标出超限被挤出的早期输出。taskId 只在创建它的 run scope 可读，绑定入口/对话/固定 sessionId，不跨聊天或 MCP 客户端。启动、查询、完成重验会话 scope；当前缓存与撤权边界见 [安全 §1.1](12-security-threat-model.md#11-此次-sudo-与-ai-托管执行的实际边界sdk-210)。

命令必须以前台进程留在托管通道。不会解析/改写任意 shell 的 `&`、nohup、daemonize，自行脱离的进程不受监控，父进程退出不能证明它完成。显式 `monitoring=true` 的无限日志流仅本地等退出或 Stop，不自动唤醒/轮询模型。

**提权是两层明确意图。** `elevated=true` 传不含 sudo 包装的实际命令，整条 root 范围包含管道和重定向；插件 Ask/ReadOnlyAuto 独立审批、不记首词批准，Bypass 只跳插件卡片，不能跳过宿主逐次可信确认（NOPASSWD 同样确认）。对外 MCP 没有审批卡：提权不在插件层拒绝，三种模式都直接请求宿主的桌面确认与密码输入（宿主那一关伪造不了、跳不过），其余写操作在 Ask/ReadOnlyAuto 下仍拒绝；initialize 的说明会告诉外部 agent 用 `elevated=true`、弹窗期间任务为 `AwaitingUser`。普通命令里直接写 `sudo` 时独立通道没有终端，sudo 一要密码就失败，回执的 `hint` 字段指回 `elevated`（不自动改写：整条换成 root 会改变 `make && sudo make install` 这类命令的语义）。密码不经过插件或模型；不是用户终端自动填充。详见 [能力 API §3](07-capability-apis.md#3-velaremoteexec--远程执行s5s6)。

**拒绝是运行级停止边界。** 插件审批返回 false/缺少 Handler，或宿主返回 AuthenticationCancelled（含拒绝 root 确认/取消密码），都会标记当前 run 已拒绝；模型请求前、工具调用前及后台终态续接检查后以 `ExecutionDenied` 强制暂停，桌面/Bridge 显示本地化暂停原因，不依赖模型遵守“不要重试”字符串。桌面/Bridge 新用户轮次会创建新 run，不能在已拒绝的原 run 内继续副作用。对外 MCP 是例外：每客户端 McpToolHost 仍只有一个固定 scope（后台任务才查得到），但拒绝只是那一次调用的结果，不封住这条连接；后续工具照常可用（例如只读放行挡下一条写命令后仍能 `list_sessions`），停不停由 MCP 客户端决定。

**审批挡位**（2026-10-25 起收紧）：「只读自动」只放行形状确定、不改东西的 `run_command` —— `sudo …` 一律照问，`env` 不在名单里（`printenv` 在），切词认空格与制表符；
`curl` 只认把显式 `http://` / `https://` 地址 GET / HEAD 到标准输出的那几个选项，写文件、上传、发数据、换方法、自定义请求头、读配置文件、非 http(s) 协议都问；
`wget` 默认落盘，只认 `-O -` / `-qO-` 与 `--spider`；名单里另有十几个带参数就改状态的命令按参数判（`ip` 只认 show / list / get，`route add`、`ifconfig eth0 down`、`mount -a`、
`hostname x`、`date -s`、`dmesg -c`、`journalctl --vacuum*`、`ss -K`、`rg --pre`、`bat --pager`、`less +!cmd` 等都问），这些命令的参数里出现引号、反斜杠、`$`、通配或花括号就不再猜 shell 会展开成什么、照问。
外部 MCP 服务器的工具一律走审批（`readOnlyHint` 只影响重试），审批的回调与挡位**每轮一份**（`McpApproval` 由调用方每轮传入）：IM 里几个聊天并发时各问各的，不串到别的聊天，
也不因为另一个聊天是「全部自动」就不问。插件自己的对外 MCP 服务在「对话」挡位**一个工具都不给**（`tools/list` 为空，initialize 说明提示切到计划或 Agent）。

桌面 MCP 管理页使用当前聊天面板的 `McpManager` 显示 Stopped / Starting / Ready / Degraded / Failed / Stopping、工具数量和脱敏错误，并提供启动、停止、重启和运行目录刷新。操作基于已保存配置；一次性连接测试不改变真实连接状态。`AutoStart=false` 必须显式启动，手动停止后自动取工具不会重启，旧工具及待审批调用随连接取消。配置删除、停用或连接参数变化会关闭旧连接，工作区权限在复用前重新校验。窗口关闭停止状态刷新并取消未完成启动；IM 桥接使用独立管理器，不受桌面按钮控制。

桌面和 IM 通过每轮 `AcquireToolsAsync` 租约持有连接；`KeepAlive=false` 在最后一个使用者释放后才断开，不中断其它并行轮次。Stdio 的 `EnvironmentInheritMode` 支持 Minimal（默认 SDK 必要系统环境）、None（仅显式变量）和 All（全部宿主变量），显式配置覆盖继承值。旧配置也默认 Minimal；代理、自定义运行时等额外环境需显式填写，All 可能向服务器暴露宿主环境秘密。

Windows Stdio 支持包含空格的可执行路径，命令与参数分开配置；含空格的参数路径需双引号包裹。针对 SDK 的 `cmd /c` 首命令引号问题，这类程序路径使用 `/d /c @` 包装，不使用二次展开参数的 `call`。真实 .NET 测试进程已在 Windows 验证环境继承/覆盖、工作目录、握手与调用、停止/重启/停用、最后租约释放及启动超时后的进程退出；这不代表 Linux/macOS 或任意第三方服务器已验收。

桌面 Agent 的 `delegate_subagent(prompt, role?, modelId?, allowWrites=false, timeoutSeconds?)` 可指定已添加的任一供应商实例下的已配置聊天模型（2026-11-18 起；父模型所在的供应商排在最前）；工具说明列出模型配置 ID、名称、所属供应商与真实型号，省略时继承委派时的父模型。主模型可自动委派有价值的独立任务，无需另外接入决策模型；小任务直接处理。选模型先按清单事实，型号 ID 明确对应知名厂商模型时可借助对其所长的了解，认不出的名称视为未知，与事实冲突时以事实为准。每轮最多 8 个任务、并行 4 个、默认 120 秒（`timeoutSeconds` 可设 30–600 秒，等审批与排队等文件修改锁的时间不计入），默认继承父轮本地/SSH 只读工具与经筛选的 MCP 工具。显式 `allowWrites=true` 开放现有本地/远端文件修改工具，保留父轮范围、禁用项、实时审批策略及拒绝停止边界；仍不能执行命令、管理会话/审批、传输文件或递归委派，MCP 仍仅只读。父子内置文件修改从读取到审批、写入共用可取消的串行锁，不协调其它聊天、外部程序或 MCP，不承诺取消/失败后回滚。任务结果包含 `allowWrites`、`modelId`、`toolsUsed` 和错误，聊天卡片实时显示模型及运行状态。独立模型使用自身凭据解析与端点范围校验；任务不保存 Key。候选覆盖所有供应商实例（以实例 ID 区分，同名实例仍是两家），未知/删除模型、图片模型和父凭据变化明确失败；工具协议拒绝不回退成无工具聊天。已配置但服务端答复「这个账号用不了此模型」（见 §1.8 末段），或其供应商拒绝凭据、额度用尽（401 / 403 / 429）、OAuth 续期失败的，在子任务未输出、未调工具时依次换父模型与其它候选（父模型所在供应商优先）重跑，卡片与结果写明替换，本轮记为不可用；这与上述配置层面的明确失败不同，不扩大候选范围。桌面故障转移后按新的父模型重排候选，IM 以本轮父模型排序；对外 MCP 以连接建立时选中模型的供应商排在最前，未选模型时取首个聊天模型所属供应商，一个聊天模型都没有才不提供委派。尚无完整供应商工具能力声明，`toolsUsed` 为空时不能认定已读取文件。详见 [实际权限边界](12-security-threat-model.md)。

Subagent 任务卡片默认折叠，显示任务摘要、角色、本地化状态、耗时、工具调用总次数和错误数量；任务组显示已结束数量。展开可查看完整请求、模型、工具明细、完整错误和 Markdown 结果，长内容在卡片内滚动。状态原位更新，保留展开状态，不强制滚到底部；首次插入与后续刷新均保留正在输出的正文 Markdown 段，避免将表格、粗体和代码围栏切成多个渲染器。

执行与结果回传：子任务由 `SubagentRunner` 执行，与界面无关。它不继承父对话，带自己的系统提示词，复用主环路的 `RecoveringChatClient` / `AgentExecution`（瞬时故障补试、截断的工具调用不执行、同参空转拦截、工具之后空答补试），以流式请求运行，最多 30 步。最终报告取最后一次工具调用之后的正文；没有最终报告或报告被截断时写入 `errors`。子任务落到终态后，`AgentRunCoordinator` 与后台命令走同一条路，把尚未取走的结果作为 `<untrusted-subagent-results>` 通知送回父模型，父轮在此之前不结束；已由 `subagent_wait` / `subagent_status` 取走的结果不重复通知，这两个工具在状态仍在变化时不计入「无进展」暂停。超时、取消或失败保留已写出的正文并以 `outputIsPartial` 标明；交回父模型的正文上限 24000 字符，卡片与历史保留完整内容。子任务用量并入会话收发计数；子任务发起的审批请求带 `Origin`，审批卡据此标明来源。运行卡片显示当前活动（正在调用的工具及目标、等待审批或等待文件修改锁）、Token 和单任务取消按钮，并随 `ChatTurnMeta.Subagents` 入库与回放；取结果的 `subagent_wait` / `subagent_status` 调用不另出工具卡。IM 桥接与对外 MCP 复用同一个 `SubagentRunner`。IM 桥接每轮一个编排器（Agent 模式），范围、挡位与审批沿用该聊天的授权，沿用父模型时使用本轮正在用的凭据，另选模型按当下设置现取；进度消息末尾显示已结束的子任务数，审批消息标明来源子任务，轮次结束时取消仍在运行的子任务。对外 MCP 每条连接一个编排器（`McpToolHost.CreateAsync`，Agent 模式且至少配置了一个聊天模型时），子任务使用 VelaShell 当前选中的聊天模型并消耗用户的模型额度；这条路不唤醒外部模型（`DeliversResults=false`），回执与工具说明要求调用方自行 `subagent_wait`；每条连接最多 32 个子任务、并行 4 个，仍在运行的子任务使连接不被闲置回收，连接关闭时一并取消；`subagent_wait` / `subagent_status` / `subagent_cancel` 不占用工具调用的串行锁。

子任务折叠头部使用插件专用主题、Lucide 小箭头和细分隔线，保留原生 Expander 的状态绑定与键盘操作。底栏用量为 `↑累计输入 ↓累计输出 | 上下文占用条 上下文 21% · 缓存 80%`：累计输入/输出从首次请求开始即显示，占用条紧挨它的百分比；整块是一个按钮（`UsageButton`）：悬停弹出 `UsageDetailView`（总量与占窗百分比徽标；按来源分段的条 —— 系统提示词 / 内置工具 / MCP 工具 / 压缩摘要 / 消息，自动压缩线 `ContextCompactor.TriggerTokens` =（窗口 − 最大输出）× 0.75 画成刻度，其后是压缩缓冲与回复预留；条下写离压缩线还有多少，接近时变警告色；各类一行；提示缓存 · 上一轮的读取-写入-未命中三截条；本会话输入-输出-思考-花费）。点击打开 `ContextPopup` 里的 `ContextDetailView`，对应 Claude Code 的 `/context all`：先给结论（当前上下文里一次没调用的 MCP 服务器占了多少工具定义、工具结果占消息的比例与最大一段、系统提示词与工具定义的固定开销、压缩已关闭时的提醒），再给 20×10 方格图（每格窗口的 1/200，含可用 / 压缩缓冲 / 回复预留）与合计表，消息、内置工具、MCP 工具可展开到单段内容、单个工具与单台服务器；浮层开着时悬停面板让位，Esc 关闭。分类来自 `SteeringChatClient` 的 `onRequest` 观察点：每次真实请求（含工具续流）发出前，`ContextBreakdown.Analyze` 拆分实际发出的消息与 `ChatOptions.Tools`（工具按名字 + 说明 + 参数 Schema 估算，MCP 工具经 `McpManager.ServerOf` 归到服务器；与对话摘要同文的 user 消息和运行内 `<run-progress-summary>` 块记作摘要），结果存在该对话的 `Breakdown` 上；面板按供应商报告的输入等比缩放（`ContextUsage`），生成中不缩放、多出的记入消息。从历史恢复的对话在下一次请求前只有总量。纯文本明细作为两个视图的 `ToString` 与读屏 HelpText。在途文本、思考和工具参数按字符权重估算并以 `~` 标记，流结束后按已报告 usage 校准，包含失败尝试及辅助请求。输入图片按固定额度估算，不含工具定义，不进入费用账本，不等于缓存写入。缓存写入：Anthropic 适配器以 `CacheCreationInputTokens` 报告；Microsoft.Extensions.AI.OpenAI 11.0 的 Chat Completions / Responses 适配器丢弃 `cache_creation_input_tokens`、`*_tokens_details.cache_write_tokens` 与 `prompt_cache_hit_tokens`，由 `CacheUsageChatClient` 经 `ModelReaderWriter` 从 SDK 原始用量补回（同一个键；读取只在缺失时补）。官方 OpenAI 不报写入，面板注明「未报告」。新会话清空，后台会话不覆盖前台。

窗口已知时，上下文文字和占用条从请求开始显示，以 `~` 标记本次输入加生成输出的动态估算；不使用会话累计用量。生成期间不显示上轮缓存命中率，结束后按最后一次请求的真实输入校准并恢复缓存信息。未知窗口仍不显示百分比。

桌面对 `AgentPausedException` 使用提示卡与 Warning 日志，继续保留中断历史和未知结果停止边界。远端执行超时并不证明进程已终止，不自动重跑；`run_command` 工具说明明确长任务可保留默认 `timeoutSeconds=0`，用 `waitSeconds` 短等待返回任务 ID。

**恢复的是模型步骤，不是整轮副作用。** 桌面聊天/Bridge 每会话串行推进，共享协调器；工具账本按 runId + CallId 复用同 id 同参的在途/完成结果，同 id 异参暂停，不把不同 id 的相同命令一概去重。工具帧只在完整 ToolCalls 步骤、参数完整验证后释放；未完成调用/推理不重放。每完成模型步骤与工具结果配对保留 checkpoint，部分正文以明确本地化续接边界保留，不承诺无法证明的无缝去重；断线前只收到空白时原样重发，不送只含空白的 assistant 消息，也不留续接边界。参数绑定错误（缺必填参数、JSON 值转不成参数类型，工具体尚未运行、没有副作用）作为工具错误交还模型改正后重调，单次不暂停，改两次参数再调对不受影响；但连着三步调了工具却一个都没真跑（参数绑定失败，或同 CallId 只交回账本里的旧结果）就以 `NoProgress` 暂停。其它工具失败仍暂停且不自动重试副作用。

正常结束却只有 role/usage/空白的模型步骤也进入恢复；正文、标准/原始思考及完整工具调用不算空。有可见正文（且这一步没有工具调用）的输出上限 / 内容过滤 / 拒绝收尾**照常完成**（2026-10-25 起）：桌面面板挂一张警示色提示卡、Bridge 在回复后附一句，不报错、不换站、不切回原站，记作健康成功；一字未吐的照旧报错、不重试、不换站；错误内容不按空回复重试；Responses 的 `response.failed`（适配器给的是一帧空更新）按服务端原话失败 —— 此前先吐了半截正文的被记成成功、解冻冷却，一字未吐的被当成空回复重试、原话丢失。工具调用之后的最终一步空答补一句「请继续」（只进那次请求、不进历史）重试**一次**，仍空则照常收尾、附说明，不记失败、不冷却，空步骤不进历史。空步骤与瞬时网络/429/适当 5xx 共用每步骤最多 2 次恢复预算（默认 400/800ms，尊重可取得的 Retry-After；超过 120 秒以专属原因暂停，不提前重试，也不先提示「正在重试」或「达到执行预算」；暂停仍带着原始 429 / 503，桌面面板首步照常据此换 Key 或故障转移），每次真实请求经 Steering 复验账号/凭据，取消/拒绝/确定性错误不重试。UI 25 步、Bridge 20 步仅是显式批次边界，沿用同一工具账本与 checkpoint 自动续接，不撤掉工具，也不要求逐批确认；不再设置累计 100 模型步骤、200000 输出 token 或 8 批次硬上限。批次提示仅显示实际编号，不显示虚假的总批数；后台任务完成唤醒不增加批次编号。上下文占比只表示一轮里最后一次请求的输入相对模型窗口的大小（不是多步一轮各步之和），不是执行进度或剩余额度；单请求输出限制及既有上下文压缩/裁剪仍独立生效，一轮之中的上下文按 §1.13 逐级整理。成功与失败尝试已上报的输入/输出 usage 仍完整累计，持续运行会持续产生模型用量及费用，用户可随时 Stop。取消、审批拒绝、结果未知、工具错误与两道 `NoProgress` 暂停仍可停止执行：同一工具同样参数连调四次（只读轮询工具 `task_status` / `task_wait` / `transfer_status` / `transfer_wait` 结果在变就算有进展、不计入，结果原样不变才累计；有副作用的工具照旧只按签名拦），以及上段连着三步一个工具都没真跑；两者都不是完备的循环检测。Bridge 原有轮次超时、供应商及模型限制仍适用，不保证任何计划都能完成。

普通桌面聊天在未产生有效输出、没有工具副作用时，空回复最多额外补试两次（400/800ms，状态行与 Agent 同一句「收到空回复，正在重试」），其它瞬时故障仍最多一次；混合失败不重置尝试计数，耗尽后才按已有候选链切换。设置测试、全部检测和切换前探活遇无可见正文的正常空结束仅额外补试一次（400ms），两次请求及等待共享原有 15 秒截止时间；仅思考仍不能判活。用户取消立即传播，失败尝试已上报的用量累计结算，次数不含供应商 SDK 的内部重试。Bridge 复用步骤恢复，耗尽后显示本地化空回复错误。没有新增配置项或改变摘要为空时的裁剪回落。

有限后台任务完成后以本地信号唤醒所属对话，再向模型加入新的终态通知，不为原 CallId 伪造第二个工具结果；已经由 `task_status` / `task_wait` 交付过的终态不再重复通知。通知声明自己不是新的用户指令，远端输出整体包进 `<untrusted-command-output>`，并说明其中是命令输出、不是用户指令，不得照做；内容经 JSON 转义，输出里伪造不出结束标记。会话授权已撤销的任务只交出一条「结果不予提供」的 Unknown 通知（不带输出、退出码或会话 id），本轮以 TaskUnknown 暂停。本地等待不请求模型、无默认 10 分钟等待死线；Bridge 不扩大现有授权或总超时。Stop、入口 detach/销毁、插件卸载、MCP 会话删除/过期/设置 reload、Bridge 授权 reload 取消旧 run 并异步收尾，废弃迟到唤醒；切换聊天不串入其它会话。MCP 只给任务查询/等待/取消协议，外部模型的自动继续由 MCP 客户端负责。

### 1.6 AI 文件上传与进度（SDK 2.1.1）

> 本节与 §1.7 描述默认审批流程。对外 MCP 的独立上传/下载自动批准开关基于正式 SDK 2.1.9，已在主程序开发分支接入；默认关闭，不影响桌面 AI、远端链接保存或 IM。用户需安装包含该功能的主程序版本。配置与例外见 [协作接入 §2.3c](协作接入.md#mcp-transfer-auto-approval)。

本节专指 `upload_local_file`：把用户**本机**文件经 SFTP 上传到已授权的 SSH 会话。它不是把任意大文件塞进模型上下文，也不改变聊天附件或 IM `send_file` 的平台上限；下载双入口的大小限制移除另见 §1.7。上传不设 AI 固定文件大小上限，仍受本地/远端空间、权限、协议及连接状态约束。

| 工具 | 行为 |
| --- | --- |
| `upload_local_file` | 本地绝对路径、远端绝对文件路径、可选会话；`overwrite=false` 默认不替换已有文件，显式覆盖也需审批。返回结构化任务快照，不让一次调用等待整份大文件 |
| `transfer_status` | 按本轮 `transferId` 查询状态、64 位已传/总字节、速率、ETA、执行代次与能否安全恢复 |
| `transfer_wait` | 短等，默认 2 秒、最大 30 秒；等待到期不取消上传 |
| `transfer_cancel` | 指定任务及预期执行代次，请求取消；“已请求”不代表远端已停止 |
| `transfer_resume` | 仅当宿主明确返回 `CanResume` 时，重新审批并验证当前目标连接后恢复，不自动从头上传 |

快照中的 `transfer_id` 关联后台任务，`generation` 区分恢复后的执行代次，`sequence` 用于忽略迟到进度。`stillRunning` 与明确状态共同判断是否还在执行；字节到齐仍可能等待验证/提交，不得把百分比满格当成成功。唯一成功终态是 `Succeeded`。失败、取消及 `Unknown` 不自动重传；提交回执丢失时必须先消歧，不能以另一个任务 id 再次覆盖目标。取消、到期、断线或插件停用之后，宿主最多再等 30 秒让后端真正停下（SFTP 取消要先排空已发出的写入、再等 `CLOSE` 应答）：停下了才算确认停写、清掉远端临时文件，没停下记 `Unknown`。SSH 断线的终态是 `Failed` / `session-disconnected` 而不是 `Cancelled`（`Cancelled` 表示有人不要这次传输了，调用方不该再发）：只有确认停写、目标确认没写入（`destinationCommitConfirmedAbsent`）才落到这一档，模型在重连之后重新发起是安全的；提交已经发出、没等到应答时的断线仍是 `Unknown` / `commit-unknown`。

宿主持有已批准上传，调用方请求和模型等待与传输寿命分离。查询/短等待不需要保持模型生成连接，更不靠不断请求模型刷新进度。AI 按所属 owner/run 隔离任务，查询及完成通知复核会话授权；撤权后的路径和结果不再提供。工具启动回执与最终完成通知分开，不能为同一 CallId 发送第二次工具结果。外部 MCP Agent 通过状态/等待工具主动获取进度，服务端不主动唤醒外部模型。

上传按流处理，不把整个文件装入内存。父目录别名解析后，按**文件身份**核验打开的源句柄（Windows 卷序列号 + 文件 id，Linux / macOS dev + inode），核验那一端不经任何链接走到；映射盘、subst 盘、硬链接名、大小写或 Unicode 规范化不同的写法都按同一个文件放行（2026-10-25 起；此前逐字比句柄的最终路径，这几种写法都被误拒）。审批显示解析后的路径；文件本身的符号链接不支持。Windows 持有拒绝写入/删除共享的源句柄；Unix 不把 FileShare 当成禁止其它写入者的保证，Linux / macOS 在传之前给源文件做一份宿主私有的快照，并与源句柄逐字节核对摘要。快照放在**源文件所在的卷**上（2026-10-25 起；此前一律拷进系统临时目录，/tmp 是 tmpfs 时几个 G 的快照直接吃内存）：源目录里的隐藏文件 `.vela-snapshot-<48 位十六进制>`，建好即删掉名字，靠打开着的描述符存活，宿主中途崩溃也不留明文副本。卷支持写时复制（Btrfs / XFS / bcachefs 的 reflink、macOS APFS 的 clonefile）时快照是瞬间完成、不占空间的克隆；否则需要约一个源文件大小的空间，宿主先查剩余空间，不够「文件大小 + 64 MiB」就在传之前以 `insufficient-space` 失败（说明需要多少、还剩多少；没传任何字节、目标确认没写入）。源目录不可写时退到系统临时目录，同样先查空间。建快照前清扫同目录崩溃遗留的快照（口径同下载临时文件）。准备阶段不会冒充已上传字节。传输完成后优先使用服务端 SHA-256，纯 SFTP 账号不支持服务端摘要时按流回读校验，可能增加约一个文件大小的下载流量；校验/提交期间仍是运行中，速率和 ETA 未知时不显示为零秒完成。当前宿主不能可靠核验重连身份与命名空间，因此明确 `CanResume=false`、恢复报不支持；没有断点自动重试或跨应用重启恢复。

桌面工具卡显示进度条、已传/总量、百分比、速率、ETA 和阶段，未知总量/准备/校验阶段使用不确定进度；失败、取消和未知不显示为绿色成功。切换聊天不改变所属任务卡；模型 Stop 只结束模型等待，原卡仍可显式取消。关闭/销毁面板、插件停用、MCP 会话删除/设置重载或 Bridge 授权重载走显式清理，不保证远端停止确认。严格 run 隔离保持不变，新的模型轮次不能查询旧轮次任务，旧卡持原 scope 管理已批准上传。

Bridge 只在没有其它命令/监控任务的独立上传本地等待期间暂停剩余轮次预算，返回模型请求时恢复原剩余预算；这段等待同时让出桥接的总并发名额（同一聊天的串行闸照旧握着），下一次调模型之前排队取回同一把闸、取回之后才恢复预算 —— 宿主确认没有时限、大文件能传几个钟头，占着名额会把别的聊天堵在闸前；纯命令/监控仍遵守原超时，人工 Stop/生命周期取消始终有效。模型 Stop 后上传继续时，Bridge 保留本地观察并发送带任务标识的最终状态，不自动重启模型。外部 MCP 活跃传输不因无工具请求被两小时空闲回收，已完成且不再活动的任务不会无限阻止回收。

AI 审批与宿主上传确认是独立两层：宿主在读取文件内容与上传前，逐任务确认来源插件、真实目标会话、本地源、**文件大小**、远端路径和覆盖策略；只允许当前任务，不继承终端/开会话授权，不提供“始终允许”。AI `Bypass` 不能跳过宿主确认；无授权闸、提示器或可用桌面窗口时拒绝。任务等待确认时仍走独立生命周期，不占用长 RPC。插件管理页撤销会取消该插件待批准及活动上传的租约，提交前再次检查；撤销后不再提供新的路径与结果，但不抹除此前已知输入或历史，也不保证已提交文件被回滚。宿主明确拒绝当前上传时，桌面/Bridge 的当前 run 强制 `ExecutionDenied` 暂停，不继续请求模型寻找替代路径；外部 MCP 仅该次调用失败，不封住整个客户端固定 run。停止（面板「停止」、换会话、关面板，IM 的 `/stop` 与轮次超时）或本轮任何一次拒绝（插件审批卡、宿主确认框、root 认证）之后，本轮还在 `Approval` 阶段的上传 / 下载（含模型发起的下载）一并撤掉：排在确认闸后的随取消撤下，已弹出的确认框随之关掉，以 `Cancelled` 收尾、什么都没写；停止之后才到的启动回执一到就撤（2026-10-25 起）。宿主宣告 `SupportsTransferWithdraw` 时逐项走条件撤回 `WithdrawPendingTransferAsync`（SDK 2.1.4，2026-10-31 起）：「还在等确认吗」与「撤下」由宿主同一步判定，宿主恰在停止那一拍批准的答 `PastApproval`、照常传，插件手里的快照落后一拍也不会撤错；各种结论都只发布宿主给的快照，绝不改发无条件取消。不支持的宿主照旧先取最新快照、仍在 `Approval` 才按代次取消，其间有一个往返的空当（见 [SDK §3.3f](../sdk/sdk-reference.md#33f-条件撤回sdk-214)）。已批准的照常传完，正常答完不撤，对外 MCP 连接里的单次拒绝也不撤。宿主撤销后无法读取结果时按 withheld/`Unknown` 安全暂停，不当作暂时网络错误反复读取。这是新上传 API 的专用强制点，不代表其它文件能力或通用 `remote.files`/本地文件 Broker 已实现。底层协议和状态定义见 [SDK §3.3b](../sdk/sdk-reference.md#33b-独立上传任务sdk-211) 与 [IPC §7.2](05-ipc-protocol.md#72-独立上传任务sdk-211)。

### 1.7 AI 双入口后台下载（SDK 2.1.2）

**下载契约已随 SDK 2.1.2 正式发布到 NuGet.org。** 宿主 src / tests 中央包、AI 显式包依赖与 `minSdkVersion` 均已升到 2.1.2（`apiLevel: 2`），不使用本地包或临时包源。下载在 Windows 与 Linux / macOS（x64、arm64）宿主上可用：Windows 与 Linux 的提交用例实际跑过（Linux 在 WSL Debian 的 ext4 与 tmpfs 上），macOS 只经 CI；仍未宣称真实 SSH / GUI 整链验证通过。

- **模型入口** `download_remote_file` 移除原 32 MiB 固定判断，改为 `StartDownloadAsync` 后台启动；`overwrite=false` 默认不覆盖，同名失败，明确覆盖仍须审批。给出的 `local_path` 与上传同一把尺：必须是完整绝对路径（Windows 上 `C:foo`、`\tmp\x` 这类会按进程当前目录补全的一律拒绝），审批之前规范化，审批卡与宿主确认框写的就是实际落点。返回结构化任务回执，含方向 Download、状态/阶段、64 位字节数、速率、ETA、代次与停止确认，不等待整文件完成。
- **远端链接入口**移除原 64 MiB 固定判断。选择保存路径后，创建绑定点击时原对话/会话的独立 scope 和普通进度卡；不是模型工具调用，不伪造模型回执或完成通知。选择器不提前截断最终目标，也不能代替逐任务宿主审批；选到已有文件时由系统保存框先确认替换，确认后按 `overwrite=true` 请求宿主确认（确认框照实写明替换）。切换聊天不串进度，关闭面板纳入 `CloseTransfersAsync`，迟到启动也清理。
- 两入口共用宿主任务、限速和资源预算，并非无限资源：上传下载合计每插件 4 实际传输、32 活动/排队、1024 生命周期回执；回执额度用尽或操作身份冲突是交给宿主之前的拒绝，工具回「启动前被拒」，不算结果未知，也不把整轮停成 TaskUnknown。会话授权、模型上下文/小文件读取、聊天附件及 IM 平台文件上限继续保留。

`transfer_status` / `transfer_wait` / `transfer_cancel` 同时适用于上传和下载。短等待默认 2 秒、最多 30 秒，到期或取消请求仅结束本次等待；下载本身默认无执行死线。显式取消针对预期代次；下载 `CanResume=false`，Unknown 不自动重下。用户工具卡按方向显示上传/下载、Approval/Transfer/Verification/Commit、字节、百分比、速率、ETA与取消；未知总量不编造百分比，满字节或校验/提交中不显示成功；工具没拿到快照（被拒、启动前挡下、回执丢失）时卡片标警示，不打「完成」的勾。`Succeeded` 要求最终提交确认；Unknown/TimedOut 且未确认停止不等于副作用结束，不合作后端实际退出前仍占槽并持有句柄。停止宽限期同上传，30 秒。

模型进度由本地观察刷新，不为每一帧请求模型或追加上下文；观察连续失败三次只把这一项报为「进度不可确认」（算结果未知），之后按 1 秒起翻倍、封顶 30 秒退避继续盯到宿主终态、撤权或插件停用，拿回新鲜快照即撤下这份不确定。协调器每任务终态仅通知一次；status/wait 已消费终态就不重复通知，`transfer_resume` 只查看原任务、不算消费，续不上时那份终态照常由完成通知交给模型；不为原 CallId 伪造第二次工具结果，路径/错误仍按不可信数据处理。严格 owner/run 隔离保留。Stop 只停止模型等待，任务/本地观察仍可继续，原卡可显式取消；关闭/销毁面板、插件停用、MCP 会话删除/设置重载和 Bridge 授权重载显式清理。Bridge沿用纯传输等待暂停剩余预算、让出总并发名额（见 §1.6）与Stop后本地观察/最终状态行为，不自动重启模型；命令/监控预算不扩大。外部 MCP 必须主动 status/wait 查询，服务端不承诺唤醒外部模型，活跃传输仍防空闲回收。

下载宿主许可独立于上传/终端/开会话，逐任务显示插件、真实会话、远端源、最终本地目标及覆盖策略；AI Bypass不能绕过，无提示器/窗口则拒绝。撤权取消待批准/活动租约，提交前重验，后续元数据脱敏，清理取消仍可进行；不回滚已提交文件。`send_file` 不读取已登记但尚未成功提交的下载目标（也不借同名旧文件外发），审批前后各核一次，审批期间文件大小或修改时间变了也不发；既有目录限制、外发审批及IM平台上限不变。

**安全提交支持 Windows 固定本地 NTFS 与 Linux / macOS（x64、arm64）的本地文件系统**：审批之前钉住目标目录链（Windows 逐段持有不共享删除的祖先目录句柄，Linux / macOS 从 `/` 起逐级不跟随链接地 `openat`、只留父目录 fd），独占随机临时文件，并相对钉住的父目录原子提交，祖先事后被改名也落不到别处；默认无替换，明确覆盖不先删目标，时间戳写任务持有的临时句柄。UNC、9p / SMB / FUSE / NFS 等其它文件系统在审批前明确拒绝，不支持的后端同样明确拒绝，都不回退直接写最终路径。按实际本地写入计数，校验长度、前后元数据与可用摘要，纯 SFTP 不强求 exec/默认二次整文件下载；这些检查不是远端原子快照保证。详见 [SDK §3.3c](../sdk/sdk-reference.md#33c-独立下载任务sdk-212)、[能力 API §2.2](07-capability-apis.md#22-独立下载任务sdk-212) 与 [安全 §1.2](12-security-threat-model.md#12-后台下载的实际安全边界sdk-212)。

### 1.8 AI 插件的供应商凭据与故障转移（2026-10-25）

1. **凭据不跟着换地址**。供应商的 Base URL 换到另一个 origin（协议、主机或有效端口不同；只改路径、大小写或写出默认端口不算）时，保存前弹独立的确认框（不再是同一个按钮点两下；
   盖在插件视图里的遮罩 + 卡片，默认焦点在「取消」，Esc 取消，Tab 只在框内循环，点遮罩不算任何选择）：
   - 填 Key 的供应商：清掉主槽、补充槽与没填覆盖地址、自带 Key 的模型的 Key（框里点名这些模型），补充槽与当前槽复位；同一次保存里新填的 Key 落进主槽。按钮「清除并保存」；
     取消时状态行写「已取消，什么都没改」，草稿留着。
   - 订阅登录的供应商（自定义 OAuth、Azure 等）：退出登录（删令牌、推进登录代次），同样清掉跟着旧地址走的模型自带 Key；框里说明正在用这家的对话与 IM 机器人会中断。
     按钮「退出登录并保存」；保存后到「管理登录」为新地址重新登录。在途的请求复验时拒绝发出，已经在路上的那一条照旧打旧地址、带旧地址的令牌（不泄露，只是这一轮作废）。
   - 确认之后要清的有了变动（别处又存了一把、同一个槽换了值、换过一次登录），提交时再拒、换一句话再问，不会把框里没列的一起清掉。
   - 地址改了还没保存时，「测试」不带已存的 Key 或登录：填 Key 的只带表单里新填的那把；订阅登录还登着就请用户先保存、在新地址登录后再测。
   - 目录页给配齐了的订阅行不摆地址框，换地址只在设置页。
2. **模型覆盖地址跨源必须自带 Key**：覆盖基地址与供应商不同源的模型，供应商的 Key（主槽、补充槽）一把都不跟去；要 Key 就勾「此模型使用独立的 API Key」。
   此前跨源时借第 1 把 Key —— 供应商换源之后为新地址填的主 Key 会被发往旧覆盖地址。设置页供应商页点名这类模型，模型页说明请求不带 Key，
   并提供「沿用供应商的第 1 把 Key」（勾上自带 Key、把主槽此刻的 Key 填进表单，点保存才生效）。订阅登录的供应商不在这条口径里（令牌的适用范围由签发方定）。
   供应商自己的地址解析不出 origin（空着或写错）时照旧只用主槽。模型这一层把覆盖地址改到别的源时，模型自带的 Key 照旧跟去（留待定）。
3. **Anthropic 环境变量只给官方主机**：Anthropic 协议没填 Key（供应商没有 Key、模型勾了自带 Key 却没填、换源清了 Key 还没填新的）时，只有基地址是 `https://api.anthropic.com`（默认端口；
   大小写、尾斜杠、`/v1` 都归一）才使用本机的 `ANTHROPIC_API_KEY` / `ANTHROPIC_AUTH_TOKEN`（只配环境变量直连官方仍可用；两个都设时 SDK 只认前者）；
   别的地址两者一起显式置空、都不带（明文 http、别的端口、带官方名字的别家主机都不算官方）。
4. **故障转移的候选**：链为空（或全是已删模型）时自动发现同目录、同型号的接入，但**默认只在同一个供应商实例、同一份凭据下换**（换了协议或地址的同一型号）；
   要换到同目录的其它账号（另一个实例或模型自带的 Key，比如公司与个人的 Copilot），在全局设置「故障转移」一节勾选「链为空时，也自动换到同目录的其它账号」
   （`AiSettings.AutoFailoverAcrossAccounts`，默认关；整段对话会发给那个账号、记在它的账上）。显式排进链的条目不受这个开关影响。存量配置升级后为关。
5. **冷却**：一把 Key 回 401（Key 本身被拒）冷却整把 60 秒，换哪个模型都绕开；回 403 / 429 只冷却「这把 Key 用在这个模型上」，同一把 Key 下的兄弟模型故障转移时照常探活。
   这把 Key 在任何模型上成功都解开整把的冷却；只对某个模型的冷却要在那个模型上成功才解。设置页 Key 行的「冷却中」只反映整把。
6. **空主槽**：移除第 1 把 Key（只清主槽的机密）而补充槽还在时，列表照样显示空着的「第 1 把 Key」（「空着，点铅笔填回」），不能显示、移除或检测，点铅笔填好、保存即落回主槽；
   「检测全部」只测有 Key 的行。
7. **切换提示卡**（2026-10-31）：故障转移换了一站、或同一模型换了一把 Key，那条回复紧跟头行挂一张「已切换接入」卡 —— 第一行「改用 供应商·模型」（供应商配了不止一把 Key 时再点名「第 N 把 Key · ●●●●末四位」，与设置页 Key 行同一写法，不露 Key 本身），
   下面逐跳写「哪一站：为什么」（限流 / 认证失败或无权使用 / 超时 / 服务端出错或过载 / 连不上 / 空回复 / 接入配置已变，服务端回过状态码的附 HTTP 码；与换站判定同一套分类）；
   这一轮答完且切换粘住（选择仍指着答上的那一站，或同一模型的新 Key 已写成当前槽、没开轮流）时补一句「之后的请求也会发到这里、记在这里的账上」。
   一轮连着换几次只更新这一张卡（超过 4 跳列头一跳、中间计数、最后两跳）；探活阶段就被跳过的候选不算一跳。没答完的一轮卡片照样留着，但不说「之后也发到这里」。
   **不进模型上下文**：卡只在界面上，发给模型的消息历史、复制整段与入库的回复正文都不含它；存档时记在这条回复的附加信息（`chat_meta` 的 `Switch`，Key 只存序号与末四位）里，
   重开会话恢复成卡片、上下文仍只由正文装配；导出 Markdown 时写成一段引用。只在聊天面板（IM 桥接没有故障转移）。

新增的全局设置只有 `AutoFailoverAcrossAccounts`（全局设置 → 故障转移，默认关，随「保存」生效）。

**模型在这个账号上不可用**（2026-11-16）：服务端以错误码或原话点名模型的 400 / 404（如 ChatGPT 账号走 Codex 时的 `model_not_found`）由 `TransientFailure.IsModelUnavailable` 识别；裸 404（多半是 Base URL 路径错）与普通 400 参数错不算。它只取决于「账号 + 模型」，因此按 403 同样处理：先换这家的其它 Key、只冷这把 Key 用在这个模型上；空链时自动发现在同型号接入之后追加**同一供应商实例、同一份凭据**下的其它聊天模型（按配置顺序；同一账号，计费与数据归属不变，不受 `AutoFailoverAcrossAccounts` 约束）；排了链照旧按链。切换卡原因写「该账号不可用此模型」。子任务与团队成员见 §1.4 委派段：未输出、未调工具时依次换父模型与委派候选重跑，该模型本轮记为不可用；调过工具后不重跑。

### 1.9 桌面对话作图、改图与剪贴板图片（2026-10-27）

- `AiSettings.ImageGenerationEnabled` 独立控制对话作图，`ImageModelId` 为可选默认值；旧配置缺少开关时，有默认模型即启用，没有则保持关闭。启用且默认值为空表示自动选择，主模型从当前供应商实例下的图片候选中传入配置 ID。`generate_image(prompt, modelId?)` / `edit_image(prompt, imageIds, modelId?)` 的候选还包含用户手动配置的默认模型，兼容跨供应商默认值；优先遵从用户明确指定，否则使用默认值。指定模型失效则拒绝，不自动换服务。工具没有 URL、Key 或任意路径参数。聊天顶栏模型不切换，也不改写全局默认值。普通聊天只提供图片工具、不开远程操作工具；计划模式不提供图片工具，Agent 模式可用。自定义提示词保留，但会补充已配置图片能力及会话图片 ID。
- 主模型无需另外的决策模型；工具描述提供候选 ID、名称和供应商，不根据名称编造价格或能力。对比图片时按用户要求对不同 `modelId` 使用完全相同提示词分别调用（没有额外的原子批量对比接口，仍受每轮四次限制）。执行前和审批后校验开关、默认值、候选归属及目标模型/协议/地址/Key 归属快照；回执含 `model`、`modelId`、`providerId`，表示请求的配置，并非上游实际模型的独立证明。切换聊天供应商后按新供应商重建候选，保留本轮计数与失败停止边界。
- `OpenAiImages` 复用现有 OpenAI SDK、凭据来源、origin/OAuth 守卫、附加头，文生图走 `/images/generations`，编辑走 `/images/edits` multipart（最多 3 张 PNG/JPEG/WebP，每张 20 MiB 内）。聊天模型只发整理后的提示词和选定参考图给图片服务，不把整个上下文直接传入图片接口；这些内容另经图片供应商处理和计费。Ask / ReadOnlyAuto 显示实际模型、地址、参考图数量与提示词审批，Bypass 跳插件审批。取消/拒绝后停止；图片 SDK 不重试，工具错误暂停本轮，已完成工具身份由原工具账本复用。每轮最多 4 次图片调用。旧的直接选择图片模型文生图入口兼容保留，已知名称自动路由和不收费探活边界不变。
- `ConversationImages` 用会话私有 ID 表管理用户附件与生成图，模型不可凭文件路径读取本机图片，也不能引用另一段对话图片。输入与生成图存 `DataDirectory/generated-images`，`ChatTurnMeta.Images` 只记录随机文件名/媒体类型；只有 PNG/JPEG/WebP 附件登记为会话图片（`/images/edits` 支持的格式，`ImageGenerationService.IsEditableInput`），GIF 只作视觉输入，不落盘、不给 ID，旧历史里存下的 GIF 引用恢复时同样筛掉；历史恢复同时恢复引用与显示，缺文件不使整段历史失败，旧历史兼容。生成工具结果只能解析本轮可信回执，不能把任意工具返回的路径当图打开。图片仍按签名、路径及 20 MiB 上限校验。删除会话时回收只被它引用的图片文件，清空历史回收全部无人引用的图片（面板里仍活着的对话所用的、清空开始之后才写下的除外），面板打开时后台回收写入满一天、无人引用的孤儿文件；引用读不全时一张不删，只认插件自己的文件名、不进子目录、跳过链接与被占用的文件。IM 桥接暂不注册图片工具，直接图片模型仍提示改用文本模型。
- Paste 优先把剪贴板位图编码为 PNG 附件，直到用户发送才外发；每条消息 4 件/每件 5 MiB、位图 2500 万像素上限不变，无位图回落编辑器原粘贴。可存档输入图获得图片 ID，后续编辑或历史恢复可引用；视觉聊天仍依赖模型能力。只接受接口直接返回的 base64 图片，不跟随供应商 URL；预览与保存按钮沿用原能力。
- 图片操作采用同格 Grid 叠放：右下角常驻三个独立34px圆形图标浮钮（Lucide `copy` 复制 / `image-down` 保存 / `fullscreen` 大图），无文字或共用底板；仅圆形表面半透明、图标不降低不透明度，悬停表面加深、键盘焦点有独立圆环。按钮具备工具提示与辅助名称、跟随动态主题；复制浮钮和大图底部的「复制图片」按钮通过所在 TopLevel 的剪贴板提供 `DataFormat.Bitmap`，从存储读取原始图片字节而非1024px缩略图或文件路径；延迟工厂每次独立解码，关闭预览或聊天后仍可粘贴，不引用视图释放的 Bitmap。状态栏与工具提示反馈成功或失败；读取失败不覆盖已有剪贴板。大图工具栏使用 WrapPanel，在窄窗口中自动换行。保存保持原选择器与原始字节。大图按原始PixelSize/当前屏幕缩放计算100%（物理像素1:1），初始窗口按图片+标题/工具条/阴影余量计算并受当前屏幕工作区限制，超大图等比缩小完整显示、不放大小图。`ImagePreviewView`显示实际百分比，支持＋/−、100%、适应窗口、Ctrl滚轮与双击切换；适应模式随可用视口重算，手动放大后双向滚动。Esc/关闭退出；面板 Detach 或离开视觉树统一关窗并释放 Bitmap，打开失败与文件丢失不使对话崩溃。
- 输入语法分离：`@` 只选工具（`@imagegen` / `@imageedit`，本地筛选、无需 SSH），`#` 选远端文件（支持 `#"带空格路径"`、补全/芯片/整块删除/发送展开），`/` 只在输入开头列本地命令。文件不再接受旧 `@/路径`，不改写已有历史文字。工具提及在发送时展开为固定工具意图而非文件读取；须启用作图、处于允许模式且有有效默认模型或当前供应商图片候选，输入菜单不请求供应商或产生计费。支持 `/clear` 新建但保留已存历史、`/resume` 历史选择、`/resume <ID>` 精确恢复或按标题筛选、`/help`；未知命令本地报错，忙态不切换对话，命令不作为模型请求。仅基础命名/语义对齐，不宣称完整 CLI 兼容。
- 本地 SDK generation/edit 报文、会话隔离、headless 当前聊天模型不变/图片显示/历史续图/计划隔离/失败不重发与设置 ID 回归可复现；不代表真实付费供应商、系统剪贴板或跨平台 GUI 验收。此实现只借鉴能力分层，未复制 cc-haha 源码或提示词。

### 1.10 聊天工具配置入口

内置/MCP 工具配置使用扳手图标，紧邻输入框内的模型入口右侧，与附件、模型、模式及发送/停止按钮同高（22px），共用一条水平中心线。输入框外的审批与用量状态行保持固定高度。审批选择器在纯对话模式隐藏时，工具配置入口仍可用；点击继续打开独立工具配置窗口。图标随插件提供，不依赖宿主图标资源。

### 1.11 紧凑聊天输入区与模型菜单

中文输入法的预编辑串在编辑光标附近叠加显示，采用与终端相同的 `SupportsPreedit` / `SetPreeditText` 路径；拼音不写入文档或撤销记录，确认后的中文仍由编辑器提交。组字期间隐藏占位提示，发送、历史回溯及引用删除快捷键不介入选词；取消、失焦或面板关闭清除叠加层。显示位置随布局与滚动调整，候选窗位置跟随串内光标，原有 Markdown 高亮和文件引用芯片保持不变。

输入区保持上方多行编辑、下方操作行：左侧「＋」用于添加附件，其后的紧凑入口显示模型及思考档位；右侧使用向上箭头图标发送，工具提示及辅助名称说明动作。模型与思考选择收进模型弹层，供应商身份继续可辨认，避免同名模型混淆；过长名称省略，为窄面板的发送按钮留空间。聊天/计划/Agent 模式位于输入框内的发送按钮旁；模型、模式及发送/停止按钮与左侧「＋」同高。调整思考强度不会持续高亮模型入口。模型弹层使用紧凑圆角列表与选中勾，底部同行显示思考强度标题与选择框，说明收进悬停提示。扳手入口紧邻模型选择右侧；输入框外的状态区固定预留一行，保留审批、用量及上下文占用条，审批显隐不改变高度。保留回复中补充消息和独立停止操作。

思考档位为默认、关闭（off）、低（low）、中（medium）、高（high）、超高（xhigh）和最高（max）。默认不设置请求的思考档位，由服务端决定，不固定等于中档或关闭。OpenAI Chat Completions 使用 `reasoning_effort`，Responses 使用 `reasoning.effort`；xhigh/max 按原值发送，Responses 的 `store: false` 可与之同时生效。Anthropic 的 xhigh/max 分别映射为 32768/65536 token 思考预算，沿用预算裁剪及协议下限规则，实际值受输出上限限制。档位能否使用取决于服务端与模型。

思考强度沿用对话内临时覆盖：不写回模型配置，选回已保存档位即可清除，切换模型时清除；明确不支持思考的模型不可调整，目录未知的模型仍允许尝试。设置更新、删除模型及故障转移后，模型入口与思考展示同步当前实际接入。此布局未加入语音输入。

### 1.12 工具调用的收纳与显示（2026-11-16）

一轮 Agent 动辄几十次工具调用，原先一次一张卡，回复被拉成一长条，结论埋在最底下。收纳只改可视树的摆放，卡片本身照旧逐张创建、入库、回放：

- **工具组**：相邻的工具卡并进一组，组头写「已执行 N 个操作」、次数最多的三种工具（`run_command ×9`）以及失败 / 被拒 / 参数错误的数量（警告图标）。运行中露出最近两张卡；模型开始写字、插入审批或提示卡、或整轮收尾时封口，未展开的组只剩一行。只有一张卡时不出组头。传输卡带进度条与取消按钮，不进组。
- **工作过程折叠**：整轮收尾时，若工具调用不少于两次且最后有结论正文，把思考、工具组与工具之间的过渡正文挪进一行「工作过程 · N 个操作 · 耗时」，默认收起；子任务组、团队卡、审批卡、图片不收。被停下、出错或没有结论正文时不收。
- **人读格式**：展开详情把参数与结果的 JSON 解开，按「键: 值」逐行排，多行字符串原样分行、嵌套缩进两格，不再显示 `<` 一类转义码；头部摘要优先取 command / path / url 等主参数。不是 JSON 的文本原样显示。
- **交给模型的编码**：工具结果与后台完成通知改用放行全部 Unicode 区段的编码器（`JavaScriptEncoder.Create(UnicodeRanges.All)`），中文不再以 `\uXXXX` 发送；`< > & ' +` 仍转义，§1.4 所述「输出里伪造不出 `</untrusted-command-output>`」不变，因此不能换成 UnsafeRelaxed。参数入库使用 relaxed 编码，只用于显示与历史。
- **历史**：每轮存的工具调用由 12 次提到 200 次，参数与结果按一轮 160K 字符的总预算均摊（每份 512–4K）。

### 1.13 运行中的上下文管理与断点续跑（2026-11-16）

§1.4 的批次自动续接让一轮可以跑任意多步，但上下文压缩原先只在用户发消息之前做一次，一轮之中每一步都带着全部工具输出，跑几十步即超出窗口，供应商拒绝请求、整轮中断。

**运行内压缩**（`RunContextCompactor`）垫在 `RecoveringChatClient` 之内、插话通道之外，每次请求模型之前按「窗口 − 输出预留」的占用逐级处理，做法参照 Claude Code 的 microcompact 与 autocompact：

| 占用 | 处理 |
| --- | --- |
| ≥ 50% | 较早的大块工具输出换成一句占位，保留调用与参数，最近 12 份不动 |
| ≥ 70% | 只保留最近 4 份工具输出 |
| ≥ 85% | 本轮较早的步骤由模型写成进度摘要（带工具参数，上限 1500 token），并进本轮起始的用户消息；切点只落在一步的开头，最近至少 2 步保留原文 |

原始消息不被修改：函数循环与检查点持有完整列表，每次按已记录的状态重新生成发送版本；状态只增不减，两次压缩之间同一前缀的结果相同，提示词缓存可以命中。消息按调用 id 或「角色 + 正文」识别，不依赖对象引用（批次续接会重建消息对象）。本轮起始的前缀（系统提示词、历史、这次的用户消息）不在处理范围内。估算按字符，供应商报告真实输入用量后只向上校准（1.0–2.5 倍）。写摘要失败时只做清理。每次处理在回复中留一道分隔条，写明清理数量与占用变化。桌面与 IM 桥接都接入，受「上下文压缩」开关控制，模型窗口未知时不处理。

**断点续跑**：历史库只存正文，工具调用、结果与后台通知只在内存中，程序退出后一轮的进展全部丢失。Agent 模式下 `AgentExecution` 每有一步完成、一份工具结果或一条后台通知就触发进展事件，面板合并 1.5 秒写一次检查点到插件数据目录 `run-checkpoints/<对话 id>.json`（先写临时文件再替换；单份结果截到 6K，最多 600 条消息；文件名只保留安全字符）。正常结束删除；被停下或出错时补写最终一份，并在回复末尾显示续跑卡；载入会话时存在检查点也显示续跑卡。「继续执行」以一条新的用户消息开启新的一轮：最近 24 条步骤原样放回（从一步的开头起），更早的以进度摘要与调用清单交代；中断时没有拿到结果的调用补一份「结果未知，先核实状态再决定是否重做」，与 §1.4「恢复的是模型步骤，不是整轮副作用」一致，不重放任何副作用。远端仍在运行的后台命令不会重新接上：续跑说明列出检查点里回过「运行中」、之后没见到终态的 `run_command`（会话、命令、最后已知状态），要求先核实再决定。删除会话、清空历史、截断时检查点一并删除；被删的会话在本进程内不再写检查点（删的正在跑时，停下的收尾不会补写），清空历史记下时刻、丢弃清空前开跑的那几轮的写入；定时写入与正常收尾的删除串在同一把锁上。IM 桥接在 Agent 模式下同样写检查点（键为 `bridge-` 加聊天标识，重启后不变），停下、超时、出错时提示 `/continue`；`/continue` 放回步骤（重启后先补回原请求）再开一轮，`/new` 丢弃旧检查点。子 Agent 与团队成员的任务同样接入运行内压缩（前缀为系统提示词与任务说明），随「上下文压缩」开关。

### 1.14 团队模式（2026-11-16）

团队启动或重试后，桌面与 IM 运行协调器在下一次主模型请求前等待团队汇总报告。等待中先到的普通任务结果随报告一并送达，停止本轮会取消等待。发给主模型的插话在下一次请求中送达，后续工具步骤保留其原有顺序。

`delegate_subagent` 适合几个互相独立的子任务；需要几个角色接力（调研 → 修改 → 审查）时，主模型调用一次 `team_run(goal, members[], tasks[], timeoutSeconds?)`。是否组团队由主模型自适应决定，不需要用户点名：本轮暴露了 `team_run` 时，系统提示词另附一段团队判据（三个以上不同专长的步骤、后一步依赖前一步、可并行调研再汇总、改动或安全结论需要独立复核，满足其中两条时倾向组团队；几次工具调用能答完、单文件修改、以执行命令为主的工作不组团队；通常 2–4 名成员），工具被停用或对外 MCP 时不附加。做法参照 Claude Code agent teams 的共享任务表与邮箱，以及 MiniMax Mavis 由引擎调度、Worker / Verifier 返工的回路。

- **定义**：成员不超过 16 个、任务不超过 32 个（2026-11-19 由 6 / 12 放宽；这只是防止失控计划一口气铺开的安全上限，具体几名由主模型按任务规模自己定——按职责配人，小任务通常 2–4 名，跨多个领域的大项目可以更多；同时在跑的仍受编排器并发上限 4 约束，每份计划开跑前都要用户确认。成员含名字、角色、可选模型、`allowWrites`，任务含负责人、`dependsOn`、可选 `verifies`）（负责人、`dependsOn`、可选 `verifies`）。名字唯一，`lead` / `all` 保留；依赖与审查目标必须存在，不能自指或成环，校验不过不启动任何任务。
- **调度由 `TeamEngine` 负责，不依赖模型轮询**：依赖都完成才开跑，同一成员同时只跑一个任务，依赖失败、取消或受阻时下游标为受阻。每个任务是 `SubagentOrchestrator` 上的托管子任务，沿用并发 4、审批、文件修改串行锁与运行卡片；托管条目不逐个唤醒主模型。每个任务默认 600 秒（30–1800）、最多 60 步；编排器的总数上限按「任务数 × 2」抬高。
- **信息流转**：上游报告以 `<upstream-results>` 附进下游任务说明；同一成员此前完成的任务摘要附进它后面的任务。成员有 `team_message`（发给队友 / `lead` / `all`）与 `team_board`（看板与已完成报告）；在跑的成员经收件箱客户端在下一步之前收到消息（与插话通道相同，已送达的每一步重发），未在跑的随下一个任务说明收到。消息与上游报告由其他模型写成，交给成员时框成数据。
- **审查回路**：审查任务以 `VERDICT: PASS` / `VERDICT: FAIL` 收尾，未给结论按 FAIL 处理；FAIL 时被审查的任务带着审查意见返工一次，返工后再审一次。
- **出错重跑与改派（2026-11-17）**：成员的一次运行失败后，编排器用 `TransientFailure.IsRetryableRun` 判断原样再跑是否可能成功，结果记在 `SubagentSnapshot.Retryable`。可重跑的包括瞬时故障（网络层错误、408 / 429 / 5xx、过载），以及错误原话表明流被上游中断的情况（如中转站的「Upstream response stream was interrupted」：流里的 error 帧只是一个不带状态码的异常，请求级补试不处理它）。服务端答复过的其余 4xx、模型拒答或输出到上限、命令结果未知导致的暂停、取消，都不重跑。引擎对可重跑的失败自动重跑同一任务，每个任务最多 2 次（`MaxAutoRetries`），期间下游不受阻；次数用完才记为失败并让下游受阻。此后仍可手动重跑：主模型的 `team_retry(taskId, assignee?)`，或团队控制台任务抽屉里的「重试 / 改派给」，两者都调用 `TeamEngine.Retry`。失败、超时、被取消的任务回到待办；对受阻任务重试等于重跑挡住它的上游；可改派给另一名成员；被挡住的下游回到待办，已经落定的团队重新打开，全部落定后再送一份汇总报告（未全部完成的报告带 `recovery` 字段提示这条路）。重跑是一次全新的运行，任务说明多一段 `## Retry`：上次因何中断、已写出的内容，并要求先核对已生效的改动再继续。出错重跑不占返工额度（返工按 `Reworks` 单独计数），`TeamTaskInfo.Retries` 记重跑次数。手动重试只在本轮进行期间可用：一轮结束后引擎随编排器释放。
- **按任务挑模型（2026-11-17）**：成员的模型由主模型在 `team_run` 的 `members[].modelId` 里指定，候选仍限定在当前供应商实例的聊天模型，省略即沿用主模型的模型。此前主模型拿到的候选只有 id 与名称，系统提示词又要求「没有充分理由就沿用父模型、不要从名称推断能力」，实际效果是全队都沿用主模型的模型。现在 `SubagentRunner.ModelCatalog` 为每个候选附上配置中已知的事实：`contextTokens`、`maxOutputTokens`、`inputPricePerMTok` / `outputPricePerMTok`、`reasoning`，并用 `parent` 标出主模型自己在用的那个；缺失的不写（单价未填、窗口是取不到规格时的默认估值、不确定是否支持思考）。清单经 `SubagentOrchestrator.ModelCatalog` 进入 `team_run` 与 `delegate_subagent` 的工具说明（桌面、IM 桥接、对外 MCP 三个入口相同）。`TeamGuidance` 与 `DelegationGuidance` 要求只按这些事实、不按模型名称分配：例行的收集与汇总用更便宜的模型，需要大量阅读的用窗口大的，设计、疑难排查与重要改动用支持思考或单价更高的，审查者尽量与被审查成员使用不同模型以便独立复核；只有一个候选或事实无差别时沿用主模型。用户的明确指定始终优先。开跑前确认卡（`DescribePlan`）上成员的模型显示名称而非配置 id。
- **跨供应商分工（2026-11-18）**：候选从「当前供应商实例」扩展到用户添加的**所有**供应商实例的聊天模型（`SubagentRunner.ModelChoices`，父模型所在的那家排在最前，不含图片模型），让主模型能按各家型号的所长分配成员。清单每条另带 `provider`（供应商实例名）与 `model`（真实型号 id）。`TeamGuidance` 与 `DelegationGuidance` 共用 `ModelSelectionGuidance`：先按上述事实分配；型号 id 明确对应知名厂商模型时，可借助主模型对其所长（写代码、长文档、多语种写作、数学、工具调用）的了解，认不出的名称（中转站别名、自定义名）视为未知，与清单事实冲突时以事实为准；审查者尽量与作者用不同模型、最好来自另一家供应商；不为「换着用」而换供应商 —— 每家单独计费，分到它的子任务读取的内容发给那一家。替补条件同步放宽为 `CannotUseModel`：型号不可用之外，401 / 403 / 429 与 OAuth 续期失败也在「未输出、未调工具」时换父模型重跑，避免某家 Key 过期让整名成员失败。上面「不按模型名称分配」一句以本条为准。
- **汇总**：全部落定后合成一份报告（各任务状态、返工次数、审查结论、报告、发给主控的消息），经与子任务结果相同的 `<untrusted-subagent-results>` 通知送回主模型。编排器判断「是否还有在途」时计入团队，等待依赖或返工的空档不会让本轮提前结束。主模型另有 `team_status`、`team_message`、`team_cancel`。
- **权限**：成员与子 Agent 相同，默认只读，`allowWrites` 须显式开启，修改走父轮审批与串行锁；`allowCommands`（默认关）开放 `run_command` 与 `task_status` / `task_wait` / `task_cancel`，每条命令经父工具箱按挡位审批、审批卡标明来源，拒绝即停止，多机并行、终端输入、会话与传输仍不开放；子任务工具中去掉主控用的 `team_status`。`delegate_subagent` 同样新增 `allowCommands`。
- **开跑前确认计划**：`team_run` 先校验，再经 `ConfirmPlanAsync` 用同一审批处理器弹出「组建团队」审批卡（`DescribePlan`：目标、成员 ✎ / >_、任务 ← 依赖 ⟲ 审查），「全部自动」放行，可「本次会话总是允许」。拒绝**不是本轮停止边界**，只把「用户没同意这个计划」退回给主模型。IM 中以审批消息发出。
- **界面（2026-11-17 改为入口卡 + 团队控制台）**：会话里只留一张两行的入口卡（`ChatPanelView.Team.cs` 的 `TeamEntryCard`）：目标与阶段芯片、成员头像叠（身份色使用宿主转发的 `VelaShellCyan` / `Blue` / `Magenta` / `Yellow` / `Green` 及 `Dim` 变体，与状态语义色分开）与「完成数 / 任务数 · 进行中 · 耗时 · 全队 token ≈合计预计花费」。整张卡可点（聚焦后 Enter / 空格同效），经 `Ui.ShowPanelAsync`（`PanelDisplayMode.Document` + `PanelPlacement.Tabs`）把 `TeamConsoleView` 开成主窗口标签组里的文档标签，标题「团队 · 目标」（目标压成一行、截到 24 字），按团队 id 去重，已开着只 `ActivateAsync`；打开失败退回独立窗口（与差异文档同一个兜底）。
  - **数据**：入口卡与控制台共用一份 `TeamConsoleSession`（最新的 `TeamBoardSnapshot`、团队任务的各次 `SubagentSnapshot`、取消入口、`TeamTelemetry` 用量序列）。`AssistantBubble.UpdateTeam` 每次刷新都推给它，控制台订阅 `Changed`、按 700 ms 合并重画（消息数变了立即画）；不在可视树上时不订阅、动画时钟停掉。一轮收尾后停在最后一版；从历史打开的是静态终态。
  - **为控制台补的快照字段**：`TeamTaskInfo.StartOffset`（开跑时距团队开跑多久，时间轴上任务条的起点）、`TeamMessageInfo.TaskId`（消息说的是哪个任务）、`TeamBoardSnapshot.LeadModelId`；引擎多记两类只给界面看的消息：`handoff`（任务开跑时，别的成员完成的上游报告交给它，挂在上游任务上）与 `review`（审查结论，挂在审查任务上，原先返工那条 `peer` 改为此类）。这些都不进模型上下文。`chat_meta` 里子任务另存 `CachedInputTokens` 与 `ContextTokens`，从历史打开时费用与上下文占用才对得上。
  - **页面**（`TeamConsoleView` 及 `.Panels` / `.Graph` / `.Drawer`，推导在纯函数的 `TeamConsoleModel`）：头部（阶段、目标、已运行）→ 六块统计 → 团队拓扑与数据流 | 成员状态 → 任务时间轴 | Token 消耗 → 通信记录；内容区不窄于 1150 px 时并排两栏。拓扑的关系由计划推出：主控指派每名成员、依赖 = 交付、`verifies` = 审查、成员间 `peer` 消息 = 协作（每对成员只留一条）；成员按依赖层数排先后、一行最多三名，主控放在直线被挡得最少的位置，被挡住的连线自动取弯度，标签避开节点与彼此。节点外环是上下文占用（最近一次请求输入 ÷ 模型窗口），状态由在跑任务的 `Activity` 推出（调工具 = 执行中、无工具 = 思考中、等审批 / 文件锁 / 依赖 = 等待中、有失败 = 阻塞）。新消息沿对应连线飞一串光点。运行中的任务没有可信的完成度，时间轴上写已耗时而不是百分比。Token 速率按 2.5 秒采样各成员的增量，只在团队运行期间记录。
  - **详情抽屉**：成员（用量、缓存命中率、上下文占用、用过的工具、负责的任务、沟通对象）、任务（负责人、审查者、前置任务、报告 —— 运行中流式追加并带取消按钮）、两人之间的对话（汇报 / 审查 / 交付类消息附对应报告、工具与那次运行的用量）；三者可以互相点过去，走过的路记成返回栈，Esc 或遮罩关闭。任务没做成（失败 / 受阻）且本轮仍在进行时，任务页显示「重试」与「改派给」。抽屉与遮罩始终在可视树上，关闭时抽屉停在页面右缘之外、遮罩透明且不接收指针：开合只改 `RenderTransform` 与 `Opacity` 的目标值，过渡总是从当前位置出发（先把抽屉瞬移到起点、下一拍再放回终点的做法会让两步都触发过渡，表现为打开时闪一下）。
  - **样式**：页面是独立文档，不在聊天面板的资源作用域下，自己并入 `AiTheme.axaml`、LiveMarkdown 的样式与 `MarkdownSkin.axaml`（从 `ChatPanelView.axaml` 抽出、两处共用；代码块底色等改键的部分在 `MarkdownSkin.Sync`）和 `TeamConsoleStyles.axaml`。配色全部绑 `Vela*` 令牌；四档底色用 `VelaBgPage` → `VelaBgSidebar` → `VelaBgInput` → `VelaBgHover`，在深浅两套主题里都保持层次。成员头像（`TeamAvatar`）是矢量拼的机器人，身份色与眼睛、配件按成员序号轮换。
  - 费用按各次运行所用模型的单价估算，缓存命中按缓存价。编排器在一轮收尾释放时，只有尚未落定的团队才记为已取消。团队任务不在子任务组里重复出现。看板随 `ChatTurnMeta.Team` 入库，报告与消息截短，未落定的按已取消保存。

### 1.15 省 Token 的文件工具与改动对比（2026-11-16）

原先读文件只能整份取回、没有任何内容搜索工具，改同一文件的几处要调用几次 patch，模型为看几十行就要拉回整份文件。

- **分段读取**：`read_local_file` / `read_remote_file` 增加 `offset`（起始行，1 起）与 `limit`（默认且最多 2000 行），输出 `行号\t内容`，截断时注明总行数与下一次的 `offset`；工具描述要求模型不要把行号前缀抄进 `oldText` / `content`。本地按行流式读取，大小上限只约束返回文本总量；远端用 SDK 2.2.0 已有的 `IRemoteFs.OpenReadAsync` 顺序流按区间读，开流失败时退回 `ReadAllBytesAsync`（仍是 256KB 上限）。含 NUL 的文件按二进制拒绝。
- **内容搜索（只读、免审批）**：`search_local_files(pattern, isRegex, path, glob, contextLines, maxMatches, ignoreCase, workspaceId)` 输出 `相对路径:行号: 内容`，跳过二进制、大于 16MB 的文件与 `.git` / `node_modules` / `bin` / `obj` 等目录，不跟进符号链接与目录联接，起点路径照常经 `LocalPathScope` 校验，正则单次匹配超时 1 秒；`find_local_files` 按 `*` / `**` / `?` / `{a,b}` 找文件。`search_remote_files` 在远端执行一条**由工具自己拼装**的 `grep -rnIsH`：模型给的每个值都整体单引号转义，pattern 经 `-e` 传入、路径放在 `--` 之后，拼不出第二条命令也伪造不了选项，所能读到的不超过本来就免审批的 `read_remote_file`，因此不走审批；超时 30 秒（远端 grep 进程不保证随之退出），默认对端是 POSIX shell。
- **多处编辑**：`patch_local_file` / `patch_remote_file` 增加 `replaceAll` 与 `edits[{oldText, newText, replaceAll}]`，按顺序应用，任何一处不匹配则整体不写，一次调用只审批一次；旧参数名保留，历史回放不受影响。
- **改动事件**：`AgentToolbox.FileChanged`（`Action<FileChange>`）在本地与远端的写入、修补、删除文件、重命名文件成功后同步触发，带改动前后全文（超出上限或非 UTF-8 为空）；`Location` 为 `local:<workspaceId>` / `remote:<sessionId>`。目录操作不发事件；订阅方异常不影响工具结果；子 Agent 工具箱沿用父工具箱的订阅。
- **界面**：工具卡按类别显示图标（`ToolIcons` 按工具名精确映射，MCP 等外部工具为插头），状态图标移到右侧；修改文件的卡片头部显示 `+N −M`，展开为插件内 Myers 行级 diff（`LineDiff`）画出的统一差异（行号、增删着色、只留改动附近 3 行）。增删底色用主题令牌 `VelaStatusConnected` / `VelaError` 叠低透明度，随 12 套命名主题派生，不新增令牌。输入框上方的「N 个文件已更改」条汇总本段对话的 `FileChange`（同一文件合并，Before 取首次、After 取末次），点文件经 `IUiApi.ShowPanelAsync`（`PanelDisplayMode.Document`）在主窗口标签区打开对比文档：默认左右并排、可切内联、上一处 / 下一处导航；同一文件复用已开标签并就地刷新，打开失败时退回独立窗口。列表按对话隔离，不入库。
- **第二轮（2026-11-17）**：
  - **宿主路由**：宿主原先把 AI 插件的所有 Document 请求都送进专属区，聊天面板占着时对比标签打不开，只能退回小窗；现在只有 `Placement = Right` 且专属区空着才进专属区，见 [`08-ui-extensions.md`](08-ui-extensions.md)。对比标签开新的之前先 `ActivateAsync` 已开的那个，保证落在同一组；退回窗口占工作区的 90%。
  - **语法高亮**：`TextMateHighlighter` 用与宿主共享的 TextMateSharp，主题与聊天代码块一致（DarkPlus / LightPlus），对完整的旧 / 新文本带状态逐行 tokenize，设有行数、行长和耗时上限，超出退回纯文本。
  - **可编辑**：并排模式改为两个 AvaloniaEdit 编辑器，右侧可编辑，防抖 300ms 重算 diff。
  - **保存**：`FileTextStore` 先读当前文件（本地经 `LocalPathScope`、远端先确认会话在线），内容和基线不一致时让用户选覆盖 / 重新载入 / 取消；写入保留 BOM，换行统一成原文件占多数的那种；不走 Agent 审批。只有片段时提供「载入完整文件」，倒着套用 patch 重建旧内容。
  - **限制**：SDK 没有关闭前的钩子，关闭有未保存修改的标签不会拦截。

### 1.16 「你应该知道」提示条（2026-11-18）

长回复里真正要用户留意的往往只有一两句，回复一滚走就找不到了。桌面面板在输入框上方（已修改文件条之上）加一条「你应该知道 (N)」，钉着主模型标出的条目。

- **由主模型标出，不另跑提取**：Agent 与计划模式下，桌面面板给主模型另加一件 `note_for_user(kind, title, detail?)` 工具，`kind` 为 `warning`（风险）/ `action`（要用户亲自去做的事）/ `info`（影响后续决定的发现）。主模型本来就读过全部上下文，顺手标一下不多花一次请求，也不把对话内容再发给任何一方；代价是取决于主模型是否按工具说明去调用 —— 说明要求少而精、不放进度与回答摘要、每轮约三条以内。没有副作用，所以计划模式也给。
- **数据**：每份对话一个 `ConversationNotes`；同标题（忽略大小写）原位更新，最多 20 条，标题 120 / 说明 600 字符截断。不另存：工具调用连同参数本来就进历史，载入会话时从中重建；用户关掉只在本次打开期间有效。
- **界面**：可折叠（默认展开），按类别配图标与语义色，可逐条或全部关掉；回复里不为这件工具出工具卡。新建、切换、载入对话时随之清空或切换。
- **范围**：对话模式不给任何工具；IM 桥接与对外 MCP 没有这条提示条，也不给这件工具。登记在内置工具目录里（只读），可在「配置工具」中停用。

### 1.17 技能（Skills，2026-11-18）

技能是写给 AI 的「某类任务怎么做」的说明，格式兼容 Anthropic Agent Skills：一个文件夹里放 `SKILL.md`（`---` 包住的头至少有 `name` 与 `description`，后面是正文指令），可附带参考文件或脚本。设计与进度见宿主仓库 `ai-plan.md` §12.3。

- **从哪儿加载**：用户级 `~/.velashell/skills/<名>/`（不随卸载插件删除）与当前选中、允许读取的本地工作区内 `.velashell/skills/<名>/`，同名时工作区优先；每轮现扫。头缺 `description`、名字不合规（字母数字 `-` `_`，64 字符内）或 `SKILL.md` 超过 256 KB 的跳过；`AiSettings.DisabledSkills` 里停用的不进来。头只按「键: 值」逐行解析（支持引号与 `>` / `|` 多行块），不是完整 YAML。
- **渐进披露**：系统提示词的 `skills` 分段只列名字与一句说明（说明截到 300 字符、最多 50 个，工作区来源标 `(workspace)`），排在用户自定义提示词之前，只在本轮真的暴露了 `load_skill` 时出现。模型按需调用 `load_skill(name)` 取正文与附带文件清单，`read_skill_file(name, path)` 读附带的文本文件。
- **安全边界**：只读、不执行脚本；`read_skill_file` 拒绝越出技能目录的路径、符号链接、二进制文件与超过 256 KB 的文件。技能指令被声明为不能越过用户的明确要求、工具规则与审批。工作区技能来自工作区文件，属于该工作区授权范围内的内容；手册提醒用户打开他人项目前留意其中的 `.velashell/skills`。
- **范围**：桌面与 IM 桥接的 Agent / 计划模式；对话模式与对外 MCP 不提供。两件工具登记在内置工具目录（只读），在「配置工具」里取消勾选 `load_skill` 即整体关闭（含斜杠调用）。「配置工具」的「技能」页：逐个启停（写 `AiSettings.DisabledSkills`）、标出来源、显示解析失败的原因，并可打开 `~/.velashell/skills` 或重新扫描。
- **斜杠调用**：用户发 `/技能名 请求` 时，送给模型的那份展开为「显式调用 + `<skill>` 正文 + 请求」，界面与历史保存原话；对话模式也可用。桌面在 `/` 候选与 `/help` 中列出技能，各入口自己的内置命令优先于同名技能（IM 的 `/use`、`/mode` 等由路由先处理）。两边的内置命令几乎不重叠，只共享技能这一层，不做统一的命令注册表。

### 1.18 扩展包（2026-11-18）

扩展包把技能、斜杠命令与 MCP 服务器打包成一个可安装的单元。叫「扩展包」而不叫「插件」，是为了不与宿主的插件体系混淆。设计与进度见宿主仓库 `ai-plan.md` §12.4。

- **清单** `velashell-extension.json`：`id`（小写字母数字 `-` `_`，也是安装目录名与 MCP 工具名前缀的一部分）、`name`、`version`、`description`，可选 `skills`（技能目录，默认 `skills/`）、`commands`（`name` / `description` / `prompt`，`{{args}}` 换成命令参数）、`mcpServers`（`stdio`：`command`、`args` 数组、`env`、相对扩展包的 `workingDirectory`；`http`：`url`、`headers`）。逐项校验，不合格整包拒绝并说明原因。
- **安装**：从文件夹或 `.zip`（清单在根下或唯一顶层文件夹下）复制到插件数据目录 `extensions/<id>/`，卸载插件时随之清除。压缩包检查越界路径（zip-slip）、项数（2 万）与解压总大小（200 MB）；从文件夹复制不跟随符号链接 / 联接点；先复制到临时目录再替换旧版本。同 `id` 再装即升级。
- **确认**：安装前列出将带来的技能、命令与每台 MCP 服务器原样的启动信息（命令、参数、工作目录、环境变量、地址、请求头），用户确认后记下这部分的指纹（`AiSettings.ExtensionPacks[].ApprovedMcpFingerprint`）。指纹对不上（升级未确认、或安装目录里的文件被改）时，该扩展包的 MCP 服务器不启动，技能与命令照常，界面提示重新确认。
- **生效**：已安装、清单可读、设置里启用。技能并进技能目录（同名时优先级最低）；命令在内置命令与同名技能之后展开；已确认的 MCP 服务器转成与手工配置同构的 `McpServerConfig`（id `ext-包id-名字`，工具名前缀 `包id_名字`），沿用现有审批、超时、并发与生命周期。桌面与 IM 桥接都生效；对外 MCP 不涉及。
- **暂不做**：钩子、扩展包之间的依赖、签名校验、在线商店与自动更新。

### 1.19 「配置工具」窗口版式（2026-11-19）

原先是「左栏 MCP 服务器概览 + 右栏一长串分组」，内置工具、技能、扩展包、各台 MCP 的工具叠在一页里，东西一多就分不清。现在参照 VS Code Copilot 的配置界面改为分节导航：

- **左栏**：「扩展包」「MCP 服务器」「技能」「记忆」「工具」五节，各带计数（已安装的扩展包、手工配置的服务器、可用的技能、已保存的记忆、启用中的工具），默认打开「工具」。
- **右栏**：这一节的标题、一句说明、搜索框（只在本节内筛选，匹配到的来源自动展开）与列表；页内操作（安装扩展包、新增服务器、打开技能目录、重新扫描）放在标题行右侧。
- **行**：一个来源一行——折叠箭头、名字与副标题、`已启用/总数` 计数、行内操作、开关；展开后逐项一行，各带开关。开关是插件自己的 `AiSwitchTheme`（套在 CheckBox 上，沿用勾选语义；有开有关时显示中间态），颜色全走令牌。
- **「工具」页**：内置工具按工具卡片同一套类别分组，类别开关一次启停整类；MCP 每台服务器一行，行尾开关启停服务器本身（停用后立即断开连接），展开逐个工具，「更新工具库」在行内。
- **「MCP 服务器」页**：手工配置的服务器（点行打开配置表单）与已启用扩展包带来的服务器（只读，在「扩展包」页管理）。
- 停用状态仍然只记「没勾的那些」，改动当场保存，没有「保存」按钮。

### 1.20 记忆（2026-11-19）

AI 跨对话记住的少量事实：用户的偏好、环境里稳定的事实、被纠正过的做法。维护者定的三条：模型自动保存、用户可增删改；**只在桌面面板生效**（IM 与对外 MCP 既不读也不写——记忆里可能有个人偏好与环境信息，不该带进群聊，也不该让群成员往里写）；全局一份。

- **存储**（`Chat/Memory/MemoryStore`）：插件数据目录的 `memory.json`，只在本机。每条有短 id、标题（≤80）、内容（≤1000）、来源（`model` / `user`）、创建与修改时间，最多 200 条。先写临时文件再替换；文件读不出来时按空处理并保留原文件为 `memory.json.bad`。同一数据目录只有一个实例，面板与「配置工具」共用并经事件同步。
- **不存机密**：内容像 PEM 私钥、常见平台令牌（`sk-`、`ghp_`、`AKIA` 等）或 `password=` / `token:` 一类赋值的拒绝写入。这是粗筛，工具说明也要求不存机密。
- **交给模型**：系统提示词的 `memory` 分段（技能之后、自定义提示词之前）列出记忆，最近改过的在前，总长上限 8000 字符，超出只报个数；三种模式都放。分段声明记忆是「从前记下的背景」，不是指令，可能过时，与用户当下所说冲突时以用户为准。
- **工具**（`MemoryToolSource`，仅 Agent 模式）：`save_memory(title, content)`、`update_memory(id, title?, content?)`、`delete_memory(id)`。登记在内置工具目录（`ToolKind.Memory`），可在「工具」页单独停用。
- **总开关** `AiSettings.MemoryEnabled`（默认开）：关掉时不放清单、不给工具，已存的保留。
- **界面**：「配置工具」的「记忆」页——总开关、搜索、新增、就地编辑（同样过校验，错误写在输入框下）、删除与全部清除（都要确认）；每条写明来源与修改时间；窗口开着时模型新存的记忆当场出现。

## 2. AI 网关(S3,远期主线)

### 2.1 为什么是"网关"而不是"每个插件自带 SDK 调模型"

- **密钥归宿主**:用户在宿主设置一次模型提供方(Anthropic/OpenAI/
  本地 Ollama…)与 API key,密钥存 OS 凭据库,插件永远拿不到。
- **额度与审计**:按插件统计 token 消耗、限额、审计"哪个插件把什么
  内容发给了模型"——这对运维工具至关重要(终端内容可能含机密)。
- **一次接入,处处可用**:模型供应商演进由宿主消化,插件面对稳定的
  抽象接口。

### 2.2 接口形态(vela.ai,权限 `ai.invoke`)

```csharp
public interface IAi
{
    Task<AiModelInfo[]> ListModelsAsync(CancellationToken ct);       // 用户配置的可用档位(如 fast/balanced/powerful,不暴露密钥)
    IAsyncEnumerable<AiDelta> ChatStreamAsync(AiRequest req, CancellationToken ct);
        // AiRequest: 档位、messages、可选 tools(插件提供的工具回调经 RPC 回插件执行)
    Task<float[][]> EmbedAsync(string model, string[] inputs, CancellationToken ct);
}
```

- 工具调用(function calling)回路:模型请求工具 → 宿主经 RPC 调插件
  的工具实现 → 结果回模型。插件工具的执行仍受其权限约束(AI 不是
  权限旁路)。
- **数据出境提示**:插件首次把 `terminal.read` 获得的内容送入
  ChatStream 时,授权提示明确"终端内容将发送给 <模型提供方>";
  设置里提供"禁止任何插件向 AI 发送终端内容"总开关。
- 宿主侧实现建议直接采用官方 SDK против各供应商;本地模型经 OpenAI
  兼容端点接入,统一在网关内路由。

### 2.3 与自动化的合流

AI 动作("总结这次部署输出并通知我")= 规则引擎的动作调 ai.invoke;
AI 触发器(异常日志语义检测)= 插件订阅终端流 + 网关判定 + 触发规则。
两套骨架拼起来即"智能运维"场景,无需新机制。
